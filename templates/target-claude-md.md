# CLAUDE.md — {{PROJECT_NAME}} (Sterling layer)

Durable conventions and project facts. The **knowledge base is the authority**, not this file. The conductor's working posture is not here: it is `agent-templates/conductor.md` in the Sterling clone, installed to this project's `.claude/agents/conductor.md` by install-agents/sync-agents and activated as the main-session agent through `"agent": "conductor"` in `.claude/settings.json` — the same source file for every project, not regenerated per project.

## Authority (the knowledge base is the source of truth)

- **The store holds what is *true now***. Consult it before acting; it supersedes memory, this file's summaries and any standalone document.
- **What lives where:** what an area does, its acceptance criteria, which files it owns → **`feature_article`** (filter by `file_keys`). Why it is that way, rejected alternatives → **`decision`**. What not to do → **`anti_pattern`**. Findings with currency → **`research_finding`** — one that measured only PART of its subject states the population and its exclusions in `answer`, because an unstated gap reads as "measured the whole question". External docs → **`reference_material`**. Board and queue → `board_query`, the TUI.
- **Ambiguity → query the store, then ask.** If it is silent or self-contradictory, stop and ask — never improvise around a gap.
- **A query result is a WINDOW, not an inventory.** `capped: true` means more matched — raise `cap` or narrow the filter; never infer absence from a capped result. `knowledge_get` is the full-fidelity read.
- **`knowledge_preflight(text)` is the pre-write conflict check.** It takes no `file_keys` — it answers for a SUBJECT. Run it before drafting a record, before a design settles and before putting a question to the user; a `verify_targets` verdict names the governing records to open BEFORE you proceed.

## Retrieval-first (consult the knowledge base before work)

- **Stage retrieval before acting** — `knowledge_query` the area you are about to touch, **articles first, code second.** The store is current reality *and* rationale; the code is only the implementation. H19 delivery helps here but does not excuse you: touching a file an article owns puts that article's substance and one-hop pointers into context on its own, and touching governed territory that **no** article owns says so loudly — but it never blocks a tool call, it cannot cover unowned territory, and it only reacts to what you already touched. A safety net under this rule, not a replacement for it.

## Reconcile-always (every affected article, every change)

- **Every change updates the knowledge base to match, before the work is done.** An un-reconciled change makes the store lie; that is drift, and drift is what breaks the store's authority.
- **Reconcile _every affected_ article, not just the primary one** — the owner of the touched files (`what_it_does`, acceptance criteria, `files[]`, a history entry) **and** any article whose described behavior or dependencies the change invalidates; follow `relies_on` / `relied_by`. New features get a new owning article; renames rewrite `file_keys` so knowledge is never orphaned.
- **Which field carries paths is PER TYPE:** `feature_article` → `files[{path, role}]`; `decision`/`anti_pattern`/`research_finding`/`todo` → `file_keys[]`; `reference_material` → `location`. A field the type does not define is refused, never silently dropped.
- **Fix a wrong record FORWARD** with `knowledge_update` — the correction supersedes the error. **Retirement is narrow:** `knowledge_retire(id, in_favor_of)` is for a genuine DUPLICATE, never for a record that is merely wrong, and never by creating a replacement beside the original. **Ask the schema, don't guess it** (`knowledge_schema`), and take the refusal as the authority over the projection. An 8-char prefix resolves when reading and updating; every destroying path (`board_remove`, `maintenance_remove`) demands the full id. **Versioned writes take `expected_version`** — a stale token refuses naming both versions rather than silently overwriting.
- **A capture declaration is LANE-SCOPED.** `no_capture` discharges the capture duty only — a bare declaration never clears the research duty. When the substance exists but its write is still in flight, declare `capture_pending` naming the target instead: pending work defers or lands on the queue, it never evaporates.
- **Concept articles — capture design the moment it settles.** One `feature_article` per recurring domain concept FAMILY, marked `concept_family`: `what_it_does` = what the concept IS + its members; `intended_behavior` = INTENT + INTERACTIONS cross-referenced by sibling slug; `files` = the owning code files. Query a concept's articles before designing in its territory; create or update the family article the moment a design settles, in any mode, and register it (the `concept_designed` MCP tool; `node "${CLAUDE_PLUGIN_ROOT}/scripts/concept-designed.mjs" --family <slug>` is the no-server fallback) so H10 holds the demand at session end. Reconcile only when what the concept IS or how it INTERACTS changed — a shared-file touch alone is not a concept change.
- **Wired, not just asked:** H7 marks the owning article of a touched file → a maintenance item (`reconcile_needed`); H10 demands the owning article for unowned territory and the concept article for a registered `concept_designed` event (`concept_article_missing` survives the session).

## Conduct rules (Sterling layer)

- **A settled ruling is not a fresh choice.** Never offer a choice between implementations of a behavior a decision or ruling index already names — read the deciding paragraph first; presenting a settled question as open manufactures a false ruling when the user picks.
- **Cite rulings by SLUG in durable pointers** (commit messages, dispatch briefs, article prose, this file): a slug names the concept and survives supersession; ids version-pin. Where space allows print both — `[slug] (knowledge_get <id>)`. Bare ids stay correct for mechanically-resolved surfaces (spawn inputs, tool parameters) and for history entries deliberately pinned to what was live then.
- **Never put a bare id in front of a HUMAN.** Any identifier shown to a person carries its human-readable name beside it — `name (id8)`, name first: names clip, ids never do. Asked to rule on "board 17204d1e", the reader has no way of knowing what that refers to, and an unanswerable question still manufactures a ruling.
- **Ask, don't guess — through the AskUserQuestion tool.** EVERY decision put to the user goes through the AskUserQuestion tool form; a question asked in prose — even a numbered section — reads as rhetorical and gets missed (user-stated 2026-08-11), so it does not count as having asked. Before the question reaches the user, run `knowledge_preflight(text)` on its subject — a `verify_targets` verdict means the store already governs it; fold the ruling into the question (or drop it) BEFORE asking.
- **Solve, don't board.** For a finding INSIDE the current task's scope or an already-selected board item, evaluate and fix it in-session; board only what genuinely cannot be done now, and say why — many smells dissolve on two minutes of checking. This is the complement of "surface smells, don't fix them": in-scope gets solved, out-of-scope gets surfaced, neither gets silently parked.
- **Close-on-commit: a commit that fulfils a board item pays it** — `board_remove` in the same breath, citing the commit. A fulfilled item left open sends a later session at work that does not need doing.
- **Dispatch briefs declare territory machine-readably.** Every code-touching dispatch prompt carries a `REVIEW-TERRITORY: ["path", …]` line — one line, a JSON array of repo-relative POSIX paths naming exactly the files the agent is to touch or review (decision `review-territory-structured-receipt-files`). Without it H22 falls back to prose-scraping the brief; H22 warns on a reviewer dispatch missing the line.
- **Sparring partner (external-model second opinion).** Consult an outside model on a design before it settles, and on a code-touching diff beside the ordinary review. **Consult before you escalate** — a technical question goes to the partner BEFORE it goes to the user; where the consult and the conductor AGREE, adopt the joint recommendation without asking; where they DISAGREE, the conductor's solution stands and gets built, the disagreement recorded in the decision record. **Advisory, never gating:** its critique is evidence the conductor weighs and reports; disagreement never blocks work. If the partner is unavailable, say so and proceed.
- **TWO-ROUND ADVERSARIAL DESIGN SPARRING for a non-trivial design, before a line is written.** Round 1 settles the SHAPE: put the problem, your own proposal, and your own objections to it, and ask where the partner disagrees. Round 2 puts the CONCRETE mechanism back as numbered questions — where state lives, what sets it, what clears it, what wins on conflict, fail-closed semantics for abnormal shapes — with your own stated answer to each, and a plain verdict demanded on the candidate you most suspect is fatal. Then verify every load-bearing claim yourself: partner output is evidence, never a verdict. Not for a routine change, a rename, or a fix whose shape is already settled.
- **Store writes go through the MCP tool surface** — never shell scripts against `.sterling/`; a server lagging the code means restart the session, not bypass. (Enforced: H15 — one rule: nothing but the MCP server writes `.sterling/sterling.db`; every other file under `.sterling/`, `config.json` included, is editable by any tool, and `config_set` has no key allowlist.)
- **When the platform disagrees with the design, STOP — never silently adapt.** Claude Code's hook, frontmatter and transcript mechanics move between versions. If verified current behavior contradicts what a record or this file assumes: report the discrepancy with the doc reference AND a proposed degraded-loud fallback, then wait for approval.
- **Mechanism inventories do not live in THIS file — the store is the census.** Never copy into CLAUDE.md what a self-describing surface already answers: record shapes (`knowledge_schema`), the hook roster (`hooks.json`), the anti-pattern set (`knowledge_query`). A summary of the store is a SECOND COPY of the store, and it rots exactly as you would expect. This file carries durable conventions and the incidents that justify them; everything else is a query.
- **Knowledge is born structured.** Conductor knowledge goes straight into a durable record (`decision` / `anti_pattern` / `research_finding` / article reconciliation) — never parked as loose prose. New records are created directly, the write echo IS the draft — never routed through an unconstrained subagent. **The two write surfaces are not interchangeable.** Work you intend to do goes on the **board** (`/sterling:task`, or `board_add` with `source:'user'`) — the only surface for wanted-but-not-done work, leaving only through the artifact-write that fulfils it (`board_remove`), never by being called done in conversation. The **maintenance queue** (`board_query source:'system'`, drained by `/sterling:drain`) is **NOT** a task board: mechanism-detected debt, every item carrying a registered `system_reason` (`reconcile_needed`, `capture_owed`, `stale_research`, `article_missing`, …), minted by the event that detected it and removed by the artifact that closes it. Never hand-park a task there to remember it.
- **Codex runs through the MCP tool, never the shell.** Every Codex consult, review or lane uses the `codex` MCP tool, with the lane's shape set explicitly at the call site: `model` (`gpt-6-astra` to spar, `gpt-5.6-sol` to review, `gpt-5.6-terra` to implement), `sandbox` (`read-only` for advisory and review lanes — an enforced filesystem boundary, not a prose instruction — `workspace-write` only to implement), `approval-policy: never`, and `config: {model_reasoning_effort: "high"}`. User-ruled 2026-09-20, verbatim: *"Add that to all instruction files, that we use the codex mcp over whatever you were doing"*. A call still running after 120s backgrounds itself and returns its result as a notification — normal, not a hang.
- **Stamp Sterling's version when reporting on Sterling.** Any feedback, assessment, or bug report this project writes about Sterling's own behavior states the version and commit it was measured against — the `version` field in the clone's `.claude-plugin/plugin.json` (the same value the session-start banner prints) plus the clone's HEAD commit, and whether the session-start banner reported an AGENT CURRENCY warning. An unstamped report cannot be triaged — only re-verified from scratch.

## Plugin mechanics — surprises worth knowing up front

- **A user-scope MCP server entry can be silently dropped under `--strict-mcp-config`.** Launched with that flag, Claude Code honors only the MCP entries explicitly supplied via `--mcp-config` — user-scope entries (and any other entry not passed that way) are ignored with no visible error. If an expected MCP tool never shows up, check the entry's scope before assuming it's misconfigured elsewhere.
- **These are documentation gaps Sterling can close at the source, not folklore for every consuming project to relearn by being burned** — prefer a self-describing refusal or a queryable introspection command over a hand-written list like this one, which is why this section stays short: it names the SHAPE of the surprise, not a per-tool inventory that drifts the moment a toolchain changes.
