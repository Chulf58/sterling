# Sterling — whole-system assessment, 2026-08-15

Companion to `sterling-plugin-retrospective-2026-08-15.md` (session evidence). This file reviews the **design**: record types, identity, tool surface, agent roster, queues, and the contract. Evidence comes from one conductor-direct session in dome-farmer (Godot/Blender, ~4,600 GDScript-and-Python-file project, ~900-record store), but the claims are about the plugin.

**If you read one section, read §7 (identity) and §12 (what is missing). The single design decision doing the most damage is that every `knowledge_update` mints a new id while every citation in practice is an id.**

---

## 6. The record type system — the types are right; one field is doing most of the work

The five author-facing types (`feature_article`, `decision`, `anti_pattern`, `research_finding`, `reference_material`) carve the space **correctly**, and I would collapse none of them. The proof is that this session used four of the five for genuinely different jobs, and no record wanted to be two types at once:

- `research_finding b3f69c14` — a measurement with two clocks and a volatility hint. Right type: it is perishable by construction (a re-export invalidates it), and `volatility_hint: fast` says so.
- `anti_pattern e2b689bb` — a behaviour that is *not wrong code* but *a wrong expectation*. No other type holds "here is the mistake, here is what it cost, here is the right way".
- `decision 553aac53` — a user ruling with `alternatives_rejected`. Nothing else records what was **declined**, and today that field was the most valuable one in the entire store (see below).
- `feature_article` — the owning prose that goes stale.

**The single best field in the system is `decision.alternatives_rejected`.** It is what made today's contradiction check possible. When I put a question to the user, a check against the store found `cd095630`, whose rejected option was *"auto-supplying a default torso — DECLINED. The user chose the visible empty row"*, with the rationale *"handing the player a part they did not pick is the wrong kind of help."* Without the rejected-alternatives field, that record would have read as "the user chose a visible torso row" — a fact about torsos. With it, it read as a **generalisable principle that my new ruling was about to contradict**, which is why I went back to the user and narrowed it explicitly rather than manufacturing a silent conflict. **No other knowledge system I have used records the roads not taken, and it is the highest-value idea in Sterling.**

**Dead weight I observed:** `feature_article.live_test_refs` (empty arrays throughout), and `state`/`state_reason` — a `state_review` maintenance item has now fired **six times** on one article (`multiplayer`) whose state is correct, and the article's own history says *"If a SIXTH state_review fires on this same article with no code change, treat the detector's threshold as the defect."* A field whose validator cries wolf six times is worse than no field.

**One real gap in the type set:** there is no type for *a measurement that is a property of a generated artefact*. The manifest's `counts` block is regenerated by a build step; four articles quote numbers derived from it; nothing links them. See §12.

## 7. Identity and supersession — the most expensive design decision, still unfixed

**Every `knowledge_update` mints a new id. Every practical citation is an id.** These two facts are incompatible, and the whole consuming project is bent around the collision:

- This project's `CLAUDE.md` instructs, in several places, *"resolve it by TITLE, never by an id, since every `knowledge_update` mints a new one"* — and then the same file cites ~40 records by id, because titles are long and ids are what tools take.
- The reconcile agent I dispatched today had to open its report with: *"None of the ids has moved — these are still current."* It spent effort establishing that its own citations were live. **That check should not exist.**
- The rotation note from the previous session recorded that a prior audit reported *"EIGHT dangling record ids"* which was a **4× over-report**: four were ordinary supersession with live successors, one was fulfilled, one deliberately removed, and only two genuinely did not resolve. So the project now carries an `anti_pattern` (`5bf1cb1d`) about *not trusting dangling-id alarms*. **A store whose id-liveness alarms are 75% false has an identity problem, not an alarm problem.**

**Can a reader tell a live record from a dead one in the surface they actually use?** No. `knowledge_query` results omit the supersedes chain (you get `supersedes_count`), so the cheap surface cannot answer it and only `knowledge_get` can. That is exactly backwards: the *browsing* surface is the one that needs liveness, and the *targeted fetch* is the one that already knows.

**The fix is not complicated.** Slugs already exist on `feature_article`. Give every type a stable slug, make every tool accept a slug wherever it accepts an id, and return the current id alongside. Then a citation written into prose in July still resolves in August without anybody auditing it.

## 8. The tool/API surface — the ranking problem, and absence you cannot establish

**What took N calls that should take one:**

- **Establishing absence is impossible.** Today's contradiction check ran `knowledge_query types:["decision","anti_pattern"]` with `rank_terms` and `cap: 200` and got `matched_filter: 635, returned: 200, capped: true`. The output then exceeded the token limit and spilled to a file. The agent correctly refused to generalise: *"435 matched records I never saw at all … Do not upgrade it."* **There is no count-only or aggregate projection**, so "does anything in the store forbid X?" cannot be answered, only sampled. For a system whose entire premise is *check the store before you decide*, that is the central gap.
- **`rank_terms` are single keywords, not prose**, and there is no way to see *why* a record ranked. With 635 matches and a 200 window, relevance ranking is doing all the work invisibly.
- **`knowledge_edit` on an array element** worked well — the librarian used a `files[path=…].role` selector and each FIND matched exactly once. This is a good API. It is also **undocumented enough that I briefed the agent to check the schema first and fall back to a whole-array rewrite**, because I did not know it would work.

**What had to be learned by rejection rather than documentation — this is the clearest evidence available, and it is embarrassing for the plugin:** this project's `CLAUDE.md` contains roughly **1,200 words** of pure Sterling API errata. A sample of what a consuming project had to discover the hard way:

- `research_finding` has **no path field at all**, and *the plugin's own template still says it uses `file_keys[]`*. Three writes were rejected for this; the project now instructs authors to put paths inside the `answer` prose.
- `volatility_hint` is a closed enum `fast|medium|stable` — `"low"` is refused.
- `current_ac` is an array of **objects**, not strings. `dependencies` is an **object** whose entries are **slugs, not paths**. `concept_family` is a **string** (the family's own slug), not a boolean. `file_baselines` is server-owned and must not be passed.
- Which field carries paths **differs per type**: `files[{path, role}]` for articles, `file_keys[]` for decisions/anti-patterns/todos, none for `reference_material`.
- `board_add` needs an `objective` or the task saves ungrouped.
- The record type is `todo` but the slash command is `/sterling:task`.

`knowledge_schema(<type>)` exists and is the right answer, and the project's own rules now say *"ask the schema, don't guess it"* — but **a schema call is a remedy for missing documentation, not documentation.** When a consuming project's onboarding file needs 1,200 words of your API's exceptions, the API is under-documented, and the template being *actively wrong* about `research_finding` means new projects inherit the error.

**The operation the design obviously wants and does not have:** a **dry-run / preflight for a proposed write** that reports which existing records it would contradict. `knowledge_preflight` exists in the tool list; I did not exercise it, so I cannot say whether it does this — but nothing in the surface I used offered it, and the contradiction check I ran by hand (one Opus agent, ~84k tokens) is exactly the shape that should be a call.

## 9. The agent roster — the constraints are the feature

**The tool lists are mostly right, and today they produced better results than unconstrained agents would have.** Three cases:

1. **`test-writer` has no Bash and no implementation reads (H4).** It therefore wrote its suite from constants I stated in the brief, and — crucially — it **flagged two risks it could not resolve** (`MPL22` and `MPL25` might go red against real data) rather than peeking. Both turned out fine. An unconstrained agent would have read the manifest, tuned the assertions to it, and produced a test that could not fail.
2. **`explorer` has no Bash.** The reconcile agent could not run a probe, so it **refused to write three numbers** and named the anti-pattern that told it not to guess. The constraint produced honesty.
3. **`coder` blocked by H5 from a test path** — it read the hook source, confirmed the block was unconditional, and reported options instead of routing around.

**Where the roster is wrong:**

- **`explorer` has no `maintenance_query`.** It is the natural agent for auditing the maintenance queue — read-only, store-aware — and it cannot see the queue. Today's first audit agent had to reach the same data through `knowledge_query types:["todo"]` and then grep `system_reason` values out of a 229-record spill file. That is a tool-list oversight, not a design position.
- **`test-writer` has `Write` but no `Edit`.** So *any* change to an existing test file is a whole-file rewrite that re-types every frozen case by hand. Today that meant a **one-word rename** (removing `and_` from a function name) forced a full retype of a file backing 925 green cases. There is a stored anti-pattern about this (`6faa528e`), which is the tell that it is a recurring structural problem. **Give `test-writer` `Edit`.** The reason to withhold it — tests should be authored, not patched — is not worth the transcription risk.
- **`librarian` has no `board_*` tools**, which is defensible, but it means a drain that needs to close a *board* item cannot, while a drain that closes a *maintenance* item can. The split is not obvious from the roster.

## 10. The board and the maintenance queue — the queue is mostly already-paid, and it says so nowhere

**Signal-to-noise, measured today:** of 11 drainable items I had verified against HEAD, **7 were PAID** (the article already matched the code) and **3 were OWED** (real stale prose), 1 unresolved. That is a **~70% false-positive rate**, and it matches the plugin's own expectation — H1's own text says *"expect much of it to be ALREADY DONE: the queue records debt the mechanism detected, not debt that is necessarily still owed."*

**A system that tells you to expect 70% of its output to be noise has mis-specified its output.** The items are raised on *file mtime versus article update time*. That detects "a file the article owns changed", which is not the same proposition as "the article is now wrong" — and the gap between those two is the entire false-positive rate.

**The queue misled in both directions today:**

- **Claiming outstanding work that was done:** 7 of 11.
- **Claiming nothing while real drift existed:** the manifest was regenerated, and **four articles carrying the literal count `358` did not go red on the number at all.** The queue raised `reconcile_needed` on the *file*, correctly, but nothing knew the prose contained a stale figure. The `mech-part-export` article's title still says `358-part`, with a dated "MEASURED 2026-08-14" annotation beside it — **the annotation did not prevent it rotting in one day.**

**One structural note:** `file_parked` items *"close at branch merge, not by drain"* — good semantics, clearly documented in H1's own output, and they were correctly excluded from every count today. That is the queue at its best: a category whose lifecycle is explicit.

**An observation about drains generating their own tail:** after the librarian closed 10 items, it reported *"21 open items remain"* — the same number I started with, because other lanes' concurrent writes raised new ones. H1's own guidance anticipates this. It is honest, but it means "drain the queue" is not a completable task in an active session, and the depth number is therefore not a progress signal.

## 11. The conductor contract — the highest-value rules are the unenforced ones

Mapping the contract against what actually has a mechanism:

| Rule | Enforced by |
|---|---|
| Capture what you learn | **H10** — fired twice today, both produced records |
| Don't edit frozen tests | **H5** — fired, held |
| Subagents can't run git / arbitrary commands | **H14** — fired, held |
| Deliver knowledge for touched paths | **H19** |
| Deliver knowledge for the dispatch subject | **H20** — 4 catches today |
| Reconcile owning articles | **H7** → queue (with the 70% noise above) |
| **The conductor opens every render/plate personally** | **Nothing** |
| **A rotation note's factual claims are true** | **Nothing** |
| **A brief's cited paths were grepped this turn** | **Nothing** |
| **"All N" claims in agent reports are verified** | **Nothing** |
| Run the suite yourself before committing | Nothing (prose only) |

**The highest-value unenforced rule is "the conductor opens the plates."** In this project it is the difference between shipping and not — the user has restated it at least three times, and it exists because green structural checks have repeatedly certified visually broken assets (28 plates once passed every check with the gun barrel pointing at the ground). Today it paid off again: I opened `tank_before/front.png` and instantly saw that my own written prediction was false. **Nothing in Sterling knows whether I looked.**

That is not a criticism that it *should* be enforced by a hook — you cannot check that a model looked at an image. But it points at something real: **Sterling has no concept of evidence that must be human- (or conductor-) witnessed before a claim built on it may be recorded.** A `decision` can cite a plate nobody opened, and the store will hold it with the same confidence as one that was.

**Second-highest: "every file path in a brief must be grepped that turn."** The rotation note itself records that four cited paths were wrong in a single previous day. Today a brief of mine again carried a wrong premise (not a path, a *behaviour*) into a fan-out. A `Grep`-before-dispatch check on paths named in an `Agent` prompt is mechanically trivial and would have caught the historical cases.

## 12. What is structurally missing

Concrete, named:

1. **A count-only projection on `knowledge_query`.** `{matched_filter}` without records, so absence can be established cheaply. Today: 635 matched, 200 returned, conclusion impossible. This is the single most important missing call.
2. **Ignore-file awareness in the H19 frontier check.** Consult `.gitignore` before declaring territory "UNOWNED". Today: 3/3 false positives on a gitignored render-output tree holding ~2,900 files, and the warning threatens an H10 demand that cannot occur. One line of code.
3. **Stable slugs on every record type, accepted everywhere an id is.** See §7. This is the structural fix, and it is one of only **two or three genuinely structural items** in this list — the rest are mechanical.
4. **A `generated_artefact` link, or `derived_from` on records that quote build output.** When `manifest.json` is regenerated, every record quoting its `counts` should be flagged *on the numbers*, not on the file mtime. Today four articles carried `358` against a true 360 and nothing noticed. This is the fix for the §10 "claiming nothing while drift existed" direction, and it is structural.
5. **A contradiction preflight** — given a draft `decision`, return records whose `alternatives_rejected` or `statement` conflict. I ran this by hand today with an Opus agent and it found a real tension (`cd095630`) that changed what I asked the user. That is too valuable to be a manual step.
6. **Handoff/rotation-note claim provenance.** The note is trusted end-to-end by the next session with zero verification, and it is the artefact a fresh session trusts *most*. At minimum, let a note distinguish **measured** claims from **predicted** ones. Today a prediction written as settled fact propagated through H1 into an agent brief. A `predictions[]` array that H1 renders as *"UNVERIFIED PREDICTION"* would have cost nothing and prevented it.
7. **`maintenance_query` on `explorer`.** Tool-list fix, trivial.
8. **`Edit` on `test-writer`.** Tool-list fix, trivial, removes a recurring transcription hazard.

## 13. What would have helped, by value

**Cheap and mechanical (do these first):**
1. `.gitignore` awareness in H19's frontier check — one line, removes a whole class of noise.
2. `maintenance_query` added to `explorer`'s tool list.
3. `Edit` added to `test-writer`'s tool list.
4. Fix the `research_finding` template — it still documents a `file_keys` field the type does not have, and new projects inherit the error.
5. A count-only / `projection: "count"` option on `knowledge_query`.

**Structural (there are genuinely only three):**
6. Stable slugs as universal identity (§7).
7. Derived-from links between generated artefacts and the records quoting their numbers (§12.4).
8. Contradiction preflight as a call rather than a hand-run agent (§12.5).

**A ranking signal for H20.** Not a removal — H20 earned its keep four times today. But delivering ~33 anti-patterns to act on 4 costs ~20–28k tokens per session. If H20 returned a relevance score and delivered full text only above a threshold, with the rest as one-line pointers, it would keep every catch at a fraction of the cost. The Bash variant (H19's pointer-only mode) already proves the pattern works.

## 14. Verdict

**I would rather work with this than without it, and it is not close.**

The strongest part is **H20 plus `alternatives_rejected`**. Together they do something no linter, test suite or code review can: they catch a defect in the *instruction* before it is multiplied across a fan-out, and they surface the decision a user already made so a new question does not silently overwrite it. Four of my own briefs were wrong today and the system caught all four before they cost anything. That is the plugin justifying itself.

The weakest part is **identity**. Every update mints a new id, every citation is an id, and the consuming project has grown a whole layer of defensive practice — resolve-by-title rules, dangling-id anti-patterns, agents that open their reports by confirming their own citations are live — to compensate for it. That layer is pure overhead created by one design choice, and fixing it would make the store's own prose trustworthy for the first time.

The most *disappointing* part is the **maintenance queue's 70% already-paid rate**, because it is so close to being good. The detection is right; the proposition is wrong. It detects "a file changed" and reports "an article is stale". Narrowing that gap — by linking records to the *values* they quote rather than the *files* they name — would turn the noisiest surface in the system into the most useful one.

*Not assessed: pipelines/runs, cleanup, init, merge, council, the TUI, H21, and the promote/link/retire/preflight calls. See §6 of the companion retrospective for the full list of what this session did not exercise.*
