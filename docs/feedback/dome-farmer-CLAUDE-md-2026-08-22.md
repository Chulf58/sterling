## ⚠⚠ BUILD. THE SESSION IS MEASURED IN WHAT SHIPPED, NOT IN WHAT WAS VERIFIED (user, 2026-08-17)

**Verbatim:** *"not alot of work in this amount of time. do bigger slices per session going forward. update the claude.md to push for actual work being done. project progress is king over being causous, code the entire thing and fix what fails"*

**THIS IS THE FIRST SECTION IN THIS FILE ON PURPOSE. It sets the DEFAULT POSTURE that every rule below is read against.** Said after a long session produced only three commits, and the diagnosis was not mystery — it was measurable, and it is the checklist of what NOT to do again:

- **36 minutes blocked on THREE separate full suite runs**, one per micro-slice.
- **Recon dispatched SERIALLY before building**, so builders sat idle waiting for a map.
- **Three commits where one bigger push would have done** — a fix, then a fix to the fix, then a document edit.
- **The session ended at a rotation instead of continuing into the next slice.**

### THE RULES

1. **CODE THE WHOLE THING, THEN FIX WHAT FAILS.** Build the complete feature — every file, every call site, the wiring — and *then* run the gates and repair the fallout. **Do NOT build a third of it, verify, build another third, verify.** Verification is a phase, not a punctuation mark.
2. **ONE BIG SLICE PER SESSION, NOT FOUR SMALL ONES.** A slice ends at a commit boundary; that does not mean every commit-able thing must be its own slice. **Fold the follow-on work in.** If fixing X reveals Y and Y is in the same territory, do Y in the same slice. ⚠⚠ **SHARPENED BY USER RULING 2026-08-21 (decision `6008a921`), verbatim: *"We need to make the slices bigger, so they take up aprrox a full session. The slices we are doing now are too small and we end up spending too much time and tokens on cold booting subagents and committing, when we could take larger slices to have fewer cold boots and fewer commits."*** THE SIZE TARGET IS EXPLICIT: **approximately ONE FULL SESSION per slice — ONE commit near the session's natural end, not one per fix.** Two costs this exists to kill: **subagent COLD BOOTS** (prefer `SendMessage` follow-ups to an agent that already holds the territory's context over spawning a fresh one; fatter briefs carrying several related units) and **COMMIT CYCLES** (each costs a ~12-minute full-suite run plus conductor attention). Unchanged: green gates before the one commit, the merge gate, design questions, commit-before-bulk-deletion, and a HARD-pressure rotation still forces a commit boundary.
3. **RUN THE FULL SUITE ONCE PER SLICE, AT THE END — NOT PER EDIT.** It costs ~12 minutes. Use `--check-only` on a file, or `-a res://test/<one_suite>.gd` on a single suite, while iterating. ⚠ **The full run before the commit is NOT negotiable and is still the conductor's own** — what changes is that it happens ONCE, not three times.
4. **DISPATCH THE BUILDERS AND THE RECON TOGETHER.** Do not wait for a map before starting work the map will not change. If a builder needs a fact, give it the fact-finding in its own brief. **A serial pipeline of agents is the slowest possible use of a ceiling of fifteen.**
5. **DO NOT STOP AT A SLICE BOUNDARY. TAKE THE NEXT ITEM.** Only two things stop the session: a genuine design question, and a merge to main. Context rotation is a real limit — but rotate *because the window is full*, never because a tidy stopping point arrived.
6. **PREFER THE FIX TO THE INVESTIGATION.** When a defect's cause is obvious enough to fix in the time it would take to prove it, fix it and let the suite adjudicate. Reserve full diagnosis for defects that resist a first fix.

### ⛔ WHAT THIS DOES **NOT** OVERRIDE — read this before citing the section above

**"Progress over caution" is about SEQUENCING AND BATCH SIZE. It is not a licence to skip a gate, and every rule below was ruled by the same user, some of them days ago.**

- ⛔ **GREEN TESTS ARE STILL NON-NEGOTIABLE.** "Fix what fails" *presumes you ran the thing that tells you what failed*. A commit still needs a green suite, `gdlint` and `gdformat --check`, run by the conductor.
- ⛔ **A DESIGN QUESTION IS STILL ALWAYS AN ASK.** Speed is never a reason to invent intent. Asking costs one form; a wrong invention costs the slice.
- ⛔ **VISUAL INSPECTION IS STILL MANDATORY AND STILL THE CONDUCTOR'S OWN EYES** — *"manually inspect visually. no shortcuts, no excuses"* (user, 2026-08-14). Structural green ticks have never covered appearance and do not now.
- ⛔ **THE VENDOR'S RULING STILL STANDS**, and a disagreement is still a defect in our instrument first.
- ⛔ **CAPTURE IS STILL DUE WHEN THE DECISION IS MADE.** It is cheap and it is what makes the *next* session fast — which is the point of this whole section.

**THE TEST, WHEN THE TWO PULL AGAINST EACH OTHER:** does the cautious step protect against something that would be **EXPENSIVE OR IRREVERSIBLE** — a wrong design, a lost asset, a silent regression the suite cannot see? Then take it. Does it merely make you **more confident about something the suite is about to tell you anyway**? Then skip it and build.

## ⚠⚠ PROGRESS IS TRACKED ON THREE LAYERS, AND THE LIVE ONE IS NOT OPTIONAL (user, 2026-08-17)

**Verbatim, mid-session:** *"you dont have a way to keep track of progress?"* → *"find a way and put it in Claude.md so it can easily be tracked"* → *"what about roadmap?"*

**THE COMPLAINT WAS FAIR AND THE DIAGNOSIS IS EXACT: the conductor was tracking everything durably and NOTHING VISIBLY.** The board and the store are excellent and the user cannot see either while work is running. From a long parallel turn the user saw prose paragraphs and had no way to answer "what is done, what is running, what is left" without asking. **A tracking system the user cannot read at a glance is not tracking; it is bookkeeping.**

### THE THREE LAYERS — each answers a DIFFERENT question. Never collapse them.

| Layer | Question it answers | Horizon | Who reads it |
|---|---|---|---|
| **`ROADMAP.md`** | *Where are we in the whole game?* | The entire project — 8 milestones, ~70 items | The user, across weeks |
| **The Sterling board** (`board_query source:"user"`) | *What work is owed, and what is its evidence?* | Across sessions; survives `/clear` | The next session |
| **The harness task list** (`TaskCreate` / `TaskUpdate` / `TaskList`) | *What is happening RIGHT NOW?* | This session only | The user, live |

### THE RULES

1. **OPEN EVERY NON-TRIVIAL SESSION BY CREATING THE TASK LIST.** One task per slice item, plus one for the gates-and-commit and one for any visual inspection owed. **Do it BEFORE the first dispatch, not after** — a list written at the end is a report, not a tracker.
2. **ONE TASK PER DISPATCHED LANE, AND THE STATUS MIRRORS THE AGENT.** `in_progress` when the agent is dispatched; `completed` only when its report is ADJUDICATED, never when it merely returns. **An agent that returns "done" does not complete a task; the conductor's check does.**
3. **THE GATES AND THE COMMIT ARE THEIR OWN TASK, AND THEY ARE `blockedBy` EVERY WRITING LANE.** This makes the real constraint visible: the suite cannot run while agents hold the tree. The user should be able to SEE why nothing is committing yet.
4. ⛔ **NEVER MARK A TASK `completed` ON A PARTIAL.** Not with a failing suite, not with a lane that returned blocked, not with "the code is written but unverified". If a lane half-lands, keep it `in_progress` and CREATE a new task naming precisely what remains.
5. **THE BOARD REMAINS THE DURABLE SURFACE AND THE TASK LIST NEVER REPLACES IT.** The task list dies with the session. Anything that must outlive it — a deferral, a design question owed, a defect with evidence — goes to the board **in the same breath**, per the board-discipline rules below. A task list entry is not a record.
6. **NAME THE ROADMAP POSITION WHEN THE SLICE CHANGES, NOT ONLY WHEN ASKED.** State the milestone and item. `ROADMAP.md`'s order is DEPENDENCY, not importance — read its preamble before claiming an item is next.
7. **WHEN THE USER ASKS "WHERE ARE WE", ANSWER FROM ALL THREE**, in this order: the roadmap item, the live lanes, the committed state. One sentence each is enough.

⚠ **THE FAILURE MODE THIS CLOSES IS NOT FORGETTING — IT IS INVISIBILITY.** The work was tracked the whole time. The user simply could not see it, and had to interrupt a parallel push to ask. **Cheap to prevent, and the interruption costs a dispatch round.**

## Conduct rules

## Reconcile-always — every affected article, every change (anti-drift)

- **Every edit, change, or new feature updates the knowledge base to match — before the work is done.** An un-reconciled change makes the store lie; that is drift. A change is not complete until the articles describe the code as it now is.
- **Reconcile _every affected_ article, not just the primary one** — the article owning the touched files, and any whose behavior or dependencies the change invalidates (follow `relies_on` / `relied_by`). New features get a new owning article; new domain concepts get a concept article (intent + interactions); renames rewrite `file_keys` so knowledge is never orphaned. **WHICH FIELD CARRIES PATHS IS PER TYPE**, and getting it wrong used to lose the data silently: a `feature_article` uses `files[{path, role}]`; `decision` / `anti_pattern` / `todo` use `file_keys[]`; a `reference_material` carries none and derives its path from `location`. **`research_finding` carries `file_keys[]` (optional)** — verified against the live 0.9.0 schema with `knowledge_schema("research_finding")` on 2026-08-22. Its complete author-settable set is `question`, `answer`, `source_urls` (**REQUIRED — pass `[]` for a finding measured off the codebase rather than the web**), `source_date`, `capture_date` (the two clocks), **`volatility_hint` — a CLOSED ENUM, `fast | medium | stable` (`"low"` is refused)**, `slug`, `stack_tags`, `derived_unconfirmed`, `scope`, `file_keys`, and **two new fields: `evidence_basis` — a CLOSED ENUM, `measured | inferred` — and `measured_by`**. There is still no `title`, no `sources`, no `confidence`. **Put the paths in `file_keys` now**; naming them in `answer` as well costs nothing. A field the type does not define is now **refused** naming the valid set, rather than dropped with the write reporting success. **TO CORRECT A WRONG RECORD, FIX IT FORWARD** — `knowledge_update` the record itself; since stable identity that is an **in-place versioned edit within one lineage** (same id, new version, prior body archived), NOT a supersession. ⚠ **THREE TOOLS, THREE DIFFERENT JOBS, DO NOT MIX THEM:** `knowledge_update` = a fix-forward DELTA inside one lineage, pass only what changed. **`knowledge_supersede(old_id, fields)`** = atomically REPLACE a ruling record — **`decision` / `anti_pattern` / `research_finding` ONLY** — where `fields` is a COMPLETE create-shaped body, not a delta; a `fields` with no slug inherits the old record's slug so the concept handle survives. **Its ORPHAN DETECTION refuses the write** when the old record enumerated 2+ numbered or bulleted rulings and the replacement leaves any of them uncovered, naming the orphaned excerpts (`orphans_acknowledged: true` proceeds and discloses). `todo` / `feature_article` / `reference_material` are refused by it, naming their real exit paths. `knowledge_retire` = a no-new-row duplicate tombstone with no replacement content (below). `status`/`superseded_by` stay server-owned and are refused if you pass them, and `/sterling:cleanup` never hard-deletes knowledge. **Retirement is NARROW:** `knowledge_retire(id, in_favor_of)` supersedes a record in favour of a named survivor so retrieval stops serving it, while provenance, inbound links and id-resolution survive. It is **not** for a record that is merely wrong — fix that forward. Its one use is a genuine **duplicate**, where two records describe one thing and the reader must be sent to the survivor; `in_favor_of` is required so a retired record always forwards somewhere. Never “retire” a record by creating a replacement beside it — two records under one slug is worse than one wrong record, because retrieval returns both and they contradict (`knowledge_create` now refuses a colliding `feature_article` slug outright).
- **A `knowledge_update` must leave the WHOLE record self-consistent.** It replaces the fields you pass and silently keeps the rest, so revising `what_it_does` while leaving `intended_behavior` or `current_ac` stating the opposite ships a record that contradicts itself — and the stale half reads as authoritative. The tool now WARNS when it detects that shape, but the warning is not a gate: before writing, list every field the change touches, and re-read the record after. Long articles are where this bites.
- **Use `knowledge_append` to extend an array** (`history`, `files`, `current_ac`) instead of retransmitting it. It goes through the same versioned path — same version bump, same re-baseline — so a short draft can no longer destroy history. `knowledge_update` still REPLACES any array you pass it. ⚠ **THERE IS NO AUTO-DRAIN ANY MORE.** A write closes a maintenance item only when you NAME it: pass `resolves: [<item ids>]` on `knowledge_update` / `knowledge_append` / `knowledge_edit` / `knowledge_split` to discharge open `reconcile_needed` / `refresh_reference` items on that record's chain. The ids are validated BEFORE the write — a bad id refuses the whole call with nothing written — and the drain rides the write's own transaction. **Anything left unnamed STAYS OPEN and is warned on the receipt**, so a reconcile that forgets `resolves` leaves its queue item behind.
- **Ask the schema, don’t guess it.** `knowledge_schema(<type>)` returns every field with `required`, its type, and any closed enum values — derived from the live schema, so it cannot drift from what a write accepts. Call it before a first write of an unfamiliar type instead of learning the shape from a rejection. To extend a long field cheaply: `knowledge_append` for arrays (`history`, `files`, `current_ac`), `knowledge_edit(id, field, find, replace)` for a passage inside a long string — `find` must match exactly once, and both zero and multiple matches are refused with the count. (This is the method; learning a type’s shape by querying an existing record is the fallback.)

### ⚠⚠ BIGGER SLICES PER AGENT. A DISPATCH THAT CHANGES A FEW LINES IS THE WRONG UNIT OF WORK (user, 2026-08-15)

**THE RULES:**
- **Before dispatching, ask "what else belongs in this agent's context?" and fold it in.** One agent doing five related store writes beats five agents doing one each.

## Board discipline — a stale board is worse than an empty one (user, 2026-07-29)

**THE BOARD IS THE FIRST THING A NEW SESSION TRUSTS, AND IT HAS BEEN WRONG.** Measured 2026-07-28: of eight open code defects re-audited, **two were already fixed and three had changed shape — 5 of 8 wrong.** None of that fails loudly; it fails by sending a session at work that does not need doing.

- **AN ITEM STATES ITS EVIDENCE, NOT ITS CONCLUSION.** Quote the deciding `file:line` or the measured number. *"Rippers face one fixed direction (`swarm.gd:1591-1593` writes an identity basis)"* can be re-checked in one grep; *"the facing is broken"* cannot, and rots invisibly.
- **RE-VERIFY AGAINST HEAD BEFORE DISPATCHING AT AN ITEM.** Refreshing an item's *blocker* is not re-checking its *defect*. One read-only audit quoting the deciding line per item is cheaper than a coder correctly refusing to re-fix working code, which has happened twice.
- **CLOSE IT IN THE SAME BREATH AS THE FIX.** If the artifact is a decision or ruling, **write that record FIRST** — an item removed with nothing behind it deletes the reasoning.
- **AN ITEM THAT IS PARTLY DONE GETS REWRITTEN, NOT REMOVED.** Say which half is answered, with evidence, and which half remains.
- **WHEN A RULING DISSOLVES A QUESTION RATHER THAN ANSWERING IT, SAY SO.** "Dissolved" and "answered" read differently to whoever finds them.
- **A DEFERRED ITEM CARRIES WHAT MUST BE RE-VERIFIED WHEN PICKED UP** — the measurement that would be invalidated, the constraint that must still hold.
- **NEVER REPEAT A COUNT OR CLAIM FROM AN ITEM WITHOUT CHECKING IT AGAINST THE RECORD THAT OWNS IT.** A "twelve" propagated through an item whose own list held ten.
- **A board too large to read is a board nobody will audit. Prune on sight.**

**TWO EXCEPTIONS, both narrow.** A detail that is load-bearing for CORRECTNESS is not fine-tuning — a probe that reports a clean pass while measuring nothing is a broken instrument, not a rough edge. And a detail the user has just asked for is the work; this rule sets the DEFAULT when nobody is choosing.

## Method: how Godot and Blender are actually used here

**GODOT HAS FOUR RUN MODES AND THEY ARE NOT INTERCHANGEABLE.** Picking the wrong one does not fail — it answers a different question and sounds confident. `--check-only` for a parse gate (fastest, no addons); the **gdUnit4 suite** for logic; `--headless -s <script>` for a spike; `--path game … -s <script>` **windowed** for anything the GPU owns. The suite is the floor for `game/**` and the probe is the floor for `main.tscn`, because **no gdUnit4 test constructs the real scene** — the peace-war cycle was broken for its entire lifetime under a green 227-case suite.

**THE PROBE IS THIS PROJECT'S SECOND TEST TIER, AND WHERE COMPOSITION BUGS LIVE.** `extends SceneTree`, `_initialize()` to set up, `_process(delta) -> bool` as a frame-driven state machine returning `true` to quit (`downed_target_probe.gd` is the pattern). To drive the real game: `load("res://main.tscn").instantiate()`, **set any `@export` BEFORE `add_child`** — instantiating does not run `_ready()`, entering the tree does — then step frames. Give each stage a settle window.

**WRITE PROBES THAT CANNOT PASS BY ACCIDENT.** Every pass value should be a POSITIVE — a count that grew, a position that moved, a latch that cleared — and each should PRINT the values it compared, not a verdict. If the pass value is a zero, add a control proving the subject was engaged and print `PROBE_INVALID` + exit 1 rather than report an unearned zero. **Print the count you acted ON, not that you acted.**

**THE RENDER IS THE ONLY TEST THAT COUNTS FOR APPEARANCE.** Six-axis orthographic at true scale with a 1 m reference cube, **plus a distance shot** — legibility at range is usually the actual requirement — plus a control in frame where one exists. **The conductor OPENS the images before repeating any claim about them.**
