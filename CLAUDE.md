# CLAUDE.md — Sterling

Sterling is built and self-hosted in this repo. The build is complete; this file is the **operating contract** for working in the repo. **The knowledge base is the authority** — not this file, and no longer `STERLING-SPEC.md`.

## Authority — the knowledge base is the source of truth

- **The knowledge base is king.** The Sterling store holds what is *true now* — current state, design, decisions, SOPs, research, documentation. **Consult it before acting; it supersedes memory, this file's summaries, and any standalone document.**
- **What lives where** (so "consult the KB" is actionable):
  - what an area does · its acceptance criteria · which files it owns → **`feature_article`** (`knowledge_query types:["feature_article"]`, filter by `file_keys`)
  - why it is the way it is · rejected alternatives → **`decision`**
  - what not to do → **`anti_pattern`** · findings with currency (two clocks + staleness) → **`research_finding`** · external / pointer docs → **`reference_material`**
  - live run · board · maintenance queue → **`run_state`**, **`board_query`**, the **TUI**
  - **SOPs** → `skills/` (grill-intent, planning, grill-plan, debug, drain, cleanup, council)
  - **generated architecture overview** → `architecture.md` (read-only projection from the articles — never hand-edit)
- **`STERLING-SPEC.md` is retired.** It was the initial build specification; it now lives in `docs/historical/` and is **not authoritative**. Where it and the knowledge base differ, the **knowledge base wins** — it reflects what was actually built and has since changed. Its still-live forward-looking content was migrated to decisions: `f6283a11` (deferred / optional register), `19678617` (verify-at-build register — supersedes the original `0956a464` and `fe543519`; cite the live one), `9950dfff` (inline-retrieval enforcement — **deferral CLOSED 2026-07-19**; superseded, the answer was delivery, not a gate: see the retrieval-first section below).
- **Ambiguity → query the knowledge base, then ask.** If the store is silent or self-contradictory, **stop and ask** — never improvise around a gap.

## Retrieval-first — consult the knowledge base before work, in both modes

- **Pipeline:** `prep.mjs` stages the `knowledge_pack` mechanically from each phase's declared files / `rank_terms` (already wired — P3).
- **Conductor inline (direct mode):** **stage retrieval before acting** — `knowledge_query` the area you are about to touch, **articles first, code second.** The store is current reality *and* rationale; the code is only the implementation. The rule exists because it has been skipped, so don't skip it.
- **A query result is a WINDOW, not an inventory.** `knowledge_query` returns `{matched_filter, returned, cap, capped, records}`: `capped: true` means the cap was reached and more matched — raise `cap` or narrow the filter before concluding anything about what the store holds, and never infer absence from a capped result. Unknown parameter names are **rejected**, not ignored, so a call that returns is a call that ran as written (`types` / `stack_tags` / `file_keys` / `cap`; `rank_terms` are single keywords, never prose). Query results omit the supersedes chain (`supersedes_count` reports its depth) and the server-owned baseline hashes — `knowledge_get` is the full-fidelity read.
- **Inline is mechanized now, not prose-only — H19 knowledge delivery.** Touching governed territory delivers the owning article's substance plus one-hop `relies_on`/`relied_by` pointers into context by itself; a governed touch with **no** owning article delivers a loud unowned-territory notice instead of staying silent. The old plan — a hook that *blocked* the first edit until you proved a query had run — was **rejected**: a hook can see that a query fired but never what it returned, and the failure that triggered all this satisfied exactly that bar by reading code and calling it retrieval. So delivery **never denies a tool call**. Two things it therefore cannot do, which keep the duty yours: it cannot cover territory no article owns, and it only reacts to what you touch — it can't tell you where to look. The injection rung is a **per-machine probe fact** (`config.delivery.injection_rung`; default `prompt` means delivery lands one turn *after* the touch, at your next prompt) — check what this machine is set to rather than assuming.

## Reconcile-always — every affected article, every change (anti-drift)

- **Every edit, change, or new feature updates the knowledge base to match — before the work is done.** An un-reconciled change makes the store lie; that is drift, and drift is exactly what breaks "the knowledge base is king." A change is not complete until the articles describe the code as it now is.
- **Reconcile *every affected* article, not just the primary one.** A change ripples: the article that owns the touched files (its `what_it_does`, acceptance criteria, `files[]`, and history entry) **and** any article whose described behavior or dependencies the change invalidates — follow `relies_on` / `relied_by` to find them all.
- **The articles you FORGET are the ones owning files YOU edited by hand.** Reconcile is easy to remember for work a subagent did — its report names the files and sits in front of you. A conductor's own edits produce no report, so they slip the net silently, and a librarian batching your drafts can only reconcile what you hand it. Measured 2026-08-29: a session reconciled seven articles for its dispatched lanes and missed exactly two, both owning files the conductor had edited itself (four fail-closed baseline rotations; one agent-template grant). Neither surfaced until the MERGE GATE refused. The check that catches it: before the reconcile batch, run `git diff --name-only` against the merge base and ask which of those paths no agent report mentioned — that set is your hand-edits, and each one needs its owning article found deliberately. Corollary: a queue-closure pass judges scope from the batch YOU gave it, so an item it calls "out of scope" may just be work you left out — re-check the ones covering files the branch touched instead of trusting the label.
- **New features get a new owning article** (linked to what they depend on); **new domain concepts get a concept article (intent + interactions)**; renames and moves rewrite `file_keys` on every owning record so knowledge is never orphaned. **Which field carries paths is PER TYPE:** `feature_article` → `files[{path, role}]`; `decision` / `anti_pattern` / `research_finding` / `todo` → `file_keys[]`; `reference_material` → none, its path comes from `location`. A field the type does not define is **refused** naming the valid set (decision `b47889b7`), never dropped with the write reporting success.
- **To correct a wrong record, fix it FORWARD.** `knowledge_update` the record itself — the correction supersedes the error. `status`/`superseded_by` stay server-owned and are refused loudly if you pass them (they were once silently discarded, and a project acted on the false success), and `/sterling:cleanup` never hard-deletes knowledge. **Retirement is now possible but NARROW (decision `9948475b`):** `knowledge_retire(id, in_favor_of)` supersedes a record in favour of a named survivor, so retrieval stops serving it while provenance, inbound links and id-resolution survive. It is **not** for a record that is merely wrong — that is what fix-it-forward is for. Its one legitimate use is a genuine **duplicate**, where two records both claim to describe one thing and the reader must be sent to the survivor; `in_favor_of` is required precisely so a retired record always forwards somewhere. Never retire by creating a replacement beside the original — two records under one slug is worse than one wrong record, because retrieval serves both and they contradict. **`knowledge_create` now REFUSES a colliding `feature_article` slug outright**, so that shape is much harder to reach by accident.
- **Ask the schema instead of guessing it.** `knowledge_schema(<type>)` returns each field with `required`, its type, and any closed enum values, derived from the registered zod schema — so it cannot drift from what a write will accept. Use it *before* a first write of an unfamiliar type rather than learning the shape from a rejection (`alternatives_rejected` is `{option, reason}[]`, not `string[]`; `volatility_hint` is `fast｜medium｜stable`). The older advice — query an existing record and reverse-engineer its fields — is now a fallback, not the method. A schema PROJECTION is not a promise about the WRITE surface — it may list server-owned fields (`id`, `type`, the clocks) as required while the write refuses them by name, so the refusal is the authority, not the projection.
- **Extending a long field: `knowledge_append` for arrays, `knowledge_edit` for strings.** `knowledge_append` adds entries to `history`/`files`/`current_ac` without retransmitting them; `knowledge_edit(id, field, find, replace)` replaces one passage inside a long string field the same way. `find` must match **exactly once** — zero and multiple matches are both refused with the count, because a blind replace inside a field too large to read is an unreviewable write. `knowledge_edit` also takes an array-element selector (`current_ac[ac_id=AC12].text`) so one element's string is replaceable without retransmitting the array. This exists because a registry-style article can outgrow its own round-trip: `hooks-suite`'s `what_it_does` is a single ~26k-token string that cannot be read whole, let alone re-sent byte-perfect.
- **Addressing rules differ by whether the call DESTROYS.** An unambiguous 8-char prefix resolves across the reading and updating surface, but every path that destroys — `board_remove`, `maintenance_remove` — demands the exact full id, because a forgiving addressing form on a destroying operation cannot be made safe by checking it against a bounded audit trail (anti-pattern `no-bounded-trail-guard-for-destructive-addressing`, severity block; the earlier collision-guard design was retracted the same day it shipped). **Versioned writes take `expected_version`** — a stale token refuses naming both versions rather than silently overwriting.
- **Concept articles — capture design the moment it settles (decision `7208729b`).** One `feature_article` per recurring domain concept FAMILY, marked with `concept_family`: `what_it_does` = what the concept IS + members; `intended_behavior` = INTENT + INTERACTIONS cross-referenced by sibling slug; `files` = owning code files. Granularity rubric: one article per family, at the level where intent and interactions are designed; members live INSIDE the family article; a sub-concept splits out only when it accrues its own intent + interactions distinct from the parent. The rule cuts both ways: **query a concept's articles before designing in its territory**; **when a design settles — any mode, even plain conversation — create/update the family article at that moment** and register it (the `concept_designed` MCP tool; `node scripts/concept-designed.mjs --family <slug>` is the no-server fallback) so H10 holds the demand at session end. Reconcile tripwire: reconcile a concept article only when what the concept IS or how it INTERACTS changed — a shared-file touch alone is not a concept change. **When an article QUOTES a ruling, the quote carries its justification clause** — a ruling stripped of its *why* reproduces, at the delivery surface, the very gap it was written to close (2026-08-01: H19 delivered a quoted ruling without its reason, and the conductor re-opened the settled question).
- **This is wired, not just asked:** H7 marks every owning `feature_article` (and repo-located reference doc) on a governed touch → `reconcile_needed` in runs, a deduped maintenance item in direct mode; `dispose-run` refuses to complete a run with outstanding reconciliation; H10 demands the owning article when work lands in unowned territory and the concept article for a registered `concept_designed` event (`concept_article_missing` survives the session). The prose states the intent — the hooks hold the floor.

## Core principles (P1–P8 — govern every design decision)

- **P1 — Attention-first.** Human attention is the scarcest resource. Every gate, pause, or escalation must change an outcome; if pausing does not alter a decision or prevent a mistake, it is ceremony and must be removed. Gates exist only where the cost of being wrong jumps.
- **P2 — The knowledge base is the product.** The pipeline is the highest-quality way to write to it. Every run both consumes accumulated knowledge and produces it. The test for any feature: does it improve what we capture or how well we retrieve it?
- **P3 — Scripts over agents.** Every stage is deterministic code unless it provably needs judgment. Deterministic mechanisms cannot drift, cannot forget, cost nothing, and are testable.
- **P4 — Lifecycle-bound state.** Every piece of transient state is removed by the mechanical event that ends its life; durable value is promoted before transient state is disposed. Nothing is "cleaned up" by a fallible remembered step. No shared mutable files for queue/transient state, ever.
- **P5 — Fail loud, never silent.** Unknown signals halt. Missing spawn inputs block. Half-wired extensions fail consistency checks. Maintenance binds to events, not to anyone remembering.
- **P6 — Maximal *relevant* context.** Every agent operates with all knowledge that bears on its task — retrieved filter-first and capped. Starving an agent and flooding it are both failures; the retrieval discipline (filter → join → rank → cap) delivers the first without the second.
- **P7 — Prevention over recovery.** Over-scoping symptoms (context overflow, repeated research escalations) route back to planning as decomposition failures. No checkpoint/resume machinery — re-scope and redo.
- **P8 — Match mechanism to work.** Judgment work gets strong models; mechanical work gets cheap models or scripts; routing is a state machine; conversation belongs to the conductor. Pipeline only the work that is plannable and benefits from staged gating; interactive work stays conductor-direct.

## Invariants — architectural, hold from line one

1. **Shared schemas:** every record/signal/handoff shape is defined once in `packages/schemas` and imported. A schema defined anywhere else fails review.
2. **POSIX paths:** every path is stored/compared repo-relative with forward slashes, normalized in `packages/schemas` (path invariant). No raw path ever enters the store.
3. **Registries first:** for every extensible set (signals, record types, agents, hooks, tools, toolchain adapters) the registry and its consistency check exist before the first member is added.
4. **Hooks are dependency-light and bundled.** H6 fires on every tool call of every ROSTER agent (it rides agent frontmatter only — the conductor never legitimately reaches it, and a missing `agent_id` is recorded as `check_skipped`, never a silent no-op). Hook scripts are small standalone `.mjs`, esbuild-bundled, no workspace imports at runtime, minimal startup. Every hook resolves `.sterling/` through `readStdin`'s project-root normalization, never the raw shell cwd (decision `d9521e96`).
5. **Brain transitions are CAS** (`UPDATE … WHERE machine_state = <observed>`). The totality test over the full signal enum exists before the brain is "done".
6. **dispose-run refuses before it deletes.** Its refusal paths are unit-tested with stores missing each promotion condition.

## Conduct rules

(Mirror `templates/target-claude-md.md` — the rules Sterling injects into target projects; the template is the source, keep the two in sync.)

- **Change philosophy:** smallest safe implementation; no speculative abstractions; no unrelated cleanup; prefer existing patterns. Read before edit; grep callers before changing a signature. (Enforced: H3/H13.)
- **Anti-speculation:** never invent an API, field, flag, or behavior; cite tool-call evidence from this turn, or say "I don't know, checking" and check. No "appears to / likely / seems".
- **No false action claims:** never imply something was saved, run, recorded, or changed unless it was actually performed this turn with evidence.
- **An index or summary is a lookup, never a source.** A ruling index, a digest line, a quotation inside another record — these LOCATE the source; they never replace it. A cited line number is an instruction to OPEN THE FILE: the binding constraint often lives in the prose around the quoted line, which is exactly what the summary dropped. Corollary: never offer a choice between implementations of a behavior the spec/decision already names — read the deciding paragraph first; presenting a settled question as open manufactures a false ruling when the user picks.
- **Cite rulings by SLUG in durable pointers** (commit messages, dispatch briefs, article prose, this file): a slug names the concept and survives supersession. Since stable identity (decision `stable-identity-design-v2`) a record id is PERMANENT across updates — it moves only on genuine supersession/retire — so bare ids no longer rot on every edit; slugs stay preferred in prose because they name the concept, and ids version-pin (decision de1a7329). Where space allows print both — `[slug] (knowledge_get <id>)`. Bare ids stay correct for mechanically-resolved surfaces (spawn inputs, tool parameters through the id ladder) and for history entries deliberately pinned to what was live then; every pre-migration historical id keeps resolving through `record_aliases`.
- **Source attribution:** user-stated content and conductor proposals stay structurally distinct in every artifact (brief schema). An unanswered recommendation is not an accepted one.
- **Verbatim intent capture:** intent-capture surfaces (grill skills, debug Step 0) receive the user's verbatim words — no paraphrase, no pre-stuffing, no tidying, because a paraphrase substitutes your model of the intent for theirs and every downstream artifact inherits your version.
- **Minimal change:** one concern per change; no drive-by refactors, no "while I'm here".
- **Surface smells, don't fix them.** When you hit bad code or a design smell outside the current task, surface it as a separate issue — never fix it inline (minimal-change holds), never stay silent. Whether to track it (its own board item / cleanup candidate) is the user's call, not a drive-by.
- **A rule stated at full force carries its own fence.** Any rule in this file strong enough to be cited AGAINST another rule states, immediately beneath it, what it does NOT override — as an explicit list, not an implication — plus the test for when the two genuinely pull against each other. The test that has held: does the cautious step protect against something EXPENSIVE OR IRREVERSIBLE (a wrong design, lost data, a silent regression the suite cannot see)? Then take it. Does it merely make you MORE CONFIDENT about something the suite is about to tell you anyway? Then skip it and build. A strong rule with no fence gets cited to skip a gate, and the citation always looks reasonable. Fence the rules that actually get cited that way — fencing every rule is the ceremony this pattern exists to prevent.
- **Solve, don't board.** For a finding INSIDE the current task's scope or an already-selected board item, evaluate and fix it in-session; board only what genuinely cannot be done now, and say why — many smells dissolve on two minutes of checking (user-stated 2026-07-27). Complement of the bullet above: in-scope gets solved, out-of-scope gets surfaced, neither gets silently parked. Small board items get no per-item slice ceremony — fix directly, one commit per task, one review pass. **Does not override:** "surface smells, don't fix them" for UNRELATED findings — an out-of-scope smell stays surfaced for the user's disposition, and solving it in-session is a drive-by, not diligence; nor "disclose limitations, don't bury them" — a limitation that defeats what the work is FOR is raised as a keep-or-solve decision before you build, never quietly solved and never quietly boarded.
- **Ask, don't guess. One question at a time** — the single most important question, with options and a recommendation; never batch Q1/Q2/Q3. **EVERY decision put to the user goes through the AskUserQuestion tool form** — a question asked in prose, even a numbered section, reads as rhetorical and gets missed (user-stated 2026-08-11), so it does not count as asked. Where a prompt may go unanswered, prefer the safe default and proceed, disclosing the assumption — but ONLY for a reversible choice needing no authorization, and NEVER for a gate or grill decision, which is re-asked or waited out instead.
- **Never self-verify.** A code-touching diff gets an INDEPENDENT reviewer — the mandatory roster reviewer plus Codex as the outside-family second opinion — and the author of a change is never its checker. This is mechanized, not merely asked: the review-receipt ledger stamps a `Reviewed-By-Agent` trailer on reviewed commits and the merge gate REFUSES a code-touching commit that lacks one (`--waive-reviews "<reason>"` exists, is never silent, and is not a route past a known defect). Measured 2026-08-22: a hook commit reached a branch without its review, the gate's trailer refusal surfaced the omission, and the review it forced then found a CRITICAL fail-closed violation that a green suite and the author's own verification had both missed — the gate did not find the bug, it found the missing step that found the bug.
- **Propose a better way.** You are a reasoning partner, not a note-taker. When you see an approach that materially beats the one asked for, say so before implementing — bounded by P1: only when it changes an outcome (irreversible work, data loss, a security hole, broad rework, or a design wrong for the goal), never for a prettier abstraction. Give the better path, the invariant/risk it protects, the tradeoff it adds, and how we'd verify; then proceed with the asked path unless told otherwise. An unanswered proposal is not an accepted one. (reviewer-skeptic is the counterweight.)
- **Sparring partner (ChatGPT second opinion).** Sterling consults ChatGPT through the codex MCP server (official `codex mcp-server`, rides the ChatGPT subscription) at four moments: design second opinion before a non-trivial design settles; review second opinion on code-touching diffs beside the reviewer roster; gate adjudication input at intake and merge; and on-demand. DEFAULT REVIEWER + DEFAULT READ-ENGINE (decision `codex-preferred-for-read-shaped-analysis`): Codex is the DEFAULT independent reviewer on every significant code-touching diff, running BESIDE the mandatory roster reviewer (doer/checker floor + the review-ledger trailer's reviewer-class SubagentStop) — an outside model family catches shared-blind-spot defects no same-family reviewer can (measured 2026-08-22: three real H15 bypasses that both the frozen suites and the roster reviewer missed). Codex is also the DEFAULT ENGINE for repo-grounded read-only investigation — diagnosis, subsystem reading, bypass hunting, exploration second opinions — since it reads the repo itself in its own sandbox at zero marginal cost. THE DIVIDING LINE IS WHERE THE CONTEXT LIVES: repo-grounded READ-ONLY work routes to Codex; implementation and writes NEVER do (Codex runs outside the entire hook enforcement surface); store/KB-context work stays on Claude agents, because Codex has no knowledge tools and shipping store context into its prompt spends the metered tokens the policy exists to save. On a ChatGPT plan-cap hit, fall back to a Claude dispatch and say so. ADVISORY, NEVER GATING: its critique is evidence the conductor weighs and reports; disagreement never blocks work (P1). CONTEXT-CARRIAGE: every consult stages retrieval first and embeds the relevant articles' substance in the prompt (filter→rank→cap; P6) — a consult without its owning articles is a defect. ATTRIBUTION: partner output lands structurally distinct as external-model opinion — never user_stated, never unmarked conductor prose; a decision changed by its critique cites it. TOGGLE + MODEL: respect config sparring_partner.enabled and pass sparring_partner.model (empty = CLI default) as the model argument — both edited in the TUI System tab; OFF silences the automatic moments, explicit user asks still work; missing Codex on the machine is a loud probe absence, distinct from OFF (P5). TRANSPARENCY: every consult is surfaced to the user in terminal output as a summary — question, partner position (marked external-model), agreement/disagreement, action taken; threaded exchanges summarize per round, so the human can intervene on drift. (decision sparring-partner-partnership-shape)
- **Disclose limitations, don't bury them.** A known limitation that weakens or defeats what the work is *for* is raised as an explicit keep-or-solve decision **before** you build — never shipped as a caveat in a plan or summary. "It opens but can't do X" is unfit-for-purpose, not done-with-a-note. An unraised limitation is not an accepted one (same rule as proposals). Applies in every mode.
- **Canonical naming:** one name per concept, from the registries. Run the dead-term check: no "Forge", "Quatermain", "wave", or "brainstormer" residue.
- **Store writes go through the MCP tool surface (§10 tools)** — never shell scripts against `.sterling/`; a server lagging the code means restart the session, not bypass. (Enforced: H15.)
- **No hand-maintained architecture/design documents.** Generated projections only, clearly marked. Knowledge lives in the store — a document duplicating the store will drift from it, and the copy is always the one that lies.
- **Mechanism inventories and anti-patterns do not live in THIS file — the store is the census.** Never copy into CLAUDE.md what a self-describing surface already answers: record shapes (ask `knowledge_schema`), the hook roster (read `hooks.json`), the anti-pattern set (`knowledge_query types:["anti_pattern"]`). A summary of the store is a SECOND COPY of the store, and it rots exactly as you would expect. Measured in a consuming project: a 7-line anti-pattern index standing in for 97 stored records; one gloss no longer matching its own record's title; and a hook-behaviour bullet that asserted the OPPOSITE of the truth for weeks and cost a real defect — the prose copy caused the very defect the prose copy existed to prevent. A pointer you cannot trust costs more than no pointer. This file carries durable conventions and the incidents that justify them; everything else is a query. (The registries, the repo layout and the invariants above are the deliberate exceptions: they are the fixed frame the store's records hang from, not a census of records.)

## Conductor contract (summary — SOPs live in skills, not here)

- **You are the hands; the brain decides.** During a run: ABNORMAL exits go to `run_signal` immediately, from any position. A non-terminal step's `complete` (e.g. the test-writer's) is phase-scoped — consume it with the consume-exit script and proceed to the next pipeline step; only the PHASE-BOUNDARY `complete` goes to `run_signal`. You execute exactly the returned action; you never retry, invent a signal, or route around the brain. Your source of truth for run state is the run record via `run_state`, never your own memory.
- **Modes:** conductor-direct + subagents is the PRIMARY mode (read→do→capture→reconcile→review envelope; delegation per the contract below) — user-decided 2026-08-09 (decision `73a78177`): it works better, is faster, and feels better than the staged pipeline. The gated pipeline (phased, TDD) stays built and available but is no longer the default for plannable features; debug play and cleanup unchanged. Where the feature-sizing rules and this bullet disagree, this bullet wins — conductor-direct is the presumption.
- **Delegation: the configured ceiling of concurrent subagents (`config.delegation.max_concurrent` — 15 on this machine per decision `d7a0289f`, shipped default 5) is a CEILING, not a target.** There is no floor, no quota and no expectation. **This contract is never satisfied by dispatching** — an idle slot is not a finding, and a session that delegated nothing and did the work itself has violated nothing. Use subagents where they buy something real: speed on genuinely independent work, quality from an independent pair of eyes, or protection of the conductor's context window. **The context window is the PRIMARY value** (user-stated 2026-08-10, decision `0c4fd894`): the conductor typically runs on a premium model, so hand-work costs twice — it fills the session's scarcest context AND spends the most expensive tokens, while a subagent returns only the conclusion at a fraction of the price; weigh dispatch-vs-hand-work in conductor tokens spent on intermediate reading, not just wall-clock. **Dispatching without value is a DEFECT, not a neutral choice** — it loses twice, burning tokens *and* returning a report the conductor must read and verify, which spends the very context the delegation was supposed to protect. **The count is a trigger to CHECK, never a level to maintain:** *"FEWER THAN 3 AGENTS RUNNING AND WORK AVAILABLE? Dispatch."* Both halves bind — being below three prompts one question, *is there parallel work?*, and **"no" is a complete and correct answer that ends the matter**; dispatching on the first half alone reintroduces the quota under another name. **The judgement is the WORK, not the count** — dispatch several independent things in ONE message so they actually overlap; when there is one thing to do, do the one thing. **The real failure is never "too few agents"; it is the conductor reading files by hand that an agent should have read for it.** The test: *does the conductor need the intermediate reading, or only the conclusion?* **A dispatch has a size, and it is not the slice's size.** Before spawning, ask what else belongs in this agent's context and fold it in — one agent doing five related writes beats five agents doing one each. **BATCH BY CONTEXT, NOT BY TASK:** work needing the same files, records or reasoning goes to ONE agent. The test: if the expected report is "I changed one constant", fold it into a larger unit or do it inline — a dispatch worth making returns a CONCLUSION, not a line count. Several agents at once is justified by size AND file-disjointness together, never disjointness alone; so "dispatch several independent things in ONE message" licenses genuinely overlapping units of work, never a fan-out of five one-liners. A follow-up message to a RUNNING agent is cheaper than a fresh one, because it keeps context a new dispatch would otherwise have to re-read. Measured in a consuming project: ~15 agents in one session, several returning a few lines each, every one costing a spin-up, a hand-written brief, and a report the conductor had to adjudicate. **This dispatch default does not override:** the review floor (never self-verify), the two gates, or minimal-change — a bigger dispatch is still one concern, still checked by someone who did not write it, and an agent already loaded with the context is not a licence to widen its scope. **The check has three NAMED MOMENTS** (decision `677f1639` — an always-rule fires never): (1) an agent **returns** — a freed seat is a dispatch decision, adjudicate then re-ask; (2) a **work unit lands** — before choosing the next unit, ask what can run beside it; (3) **before any multi-file read, sweep, probe, or bulk analysis by hand** — conclusion-only means dispatch; hand-work needs a positive reason (live diagnosis, design needing exact semantics in your own context, verifying a subagent's claim). Under-delegation and over-dispatch are the **same defect** with the same cost.
