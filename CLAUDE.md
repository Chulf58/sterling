## Authority (the knowledge base is the source of truth)

- **The store holds what is *true now***. Consult it before acting; it supersedes memory, this file's summaries and any standalone document.
- **What lives where:** what an area does, its acceptance criteria, which files it owns → **`feature_article`** (filter by `file_keys`). Why it is that way, rejected alternatives → **`decision`**. What not to do → **`anti_pattern`**. Findings with currency → **`research_finding`** — one that measured only PART of its subject states the population and its exclusions in `answer`, because an unstated gap reads as "measured the whole question". External docs → **`reference_material`**. Board and queue → `board_query`, the TUI. SOPs → `skills/`. Architecture → `architecture.md` (generated; never hand-edit).
- **Ambiguity → query the store, then ask.** If it is silent or self-contradictory, stop and ask — never improvise around a gap.
- **A query result is a WINDOW, not an inventory.** `capped: true` means more matched — raise `cap` or narrow the filter; never infer absence from a capped result. `knowledge_get` is the full-fidelity read. `projection:"digest"` buys a cheap wide landscape; `min_score` answers the absence question a capped window cannot.
- **`knowledge_preflight(text)` is the pre-write conflict check.** It takes no `file_keys` — it answers for a SUBJECT. Run it before drafting a record, before a design settles and before putting a question to the user; a `verify_targets` verdict names the governing records to open BEFORE you proceed. **Phrase the text in the domain's own terms:** the matcher is lexical and a paraphrase misses (fresh blind baseline 2026-09-22, finding `fresh-blind-case-set-frozen-lexical-baseline-september-2026`: every miss was a paraphrased preflight prompt, every author-phrased query hit); after an `ungoverned` verdict on a subject you expect to be governed, re-ask once with the store's vocabulary — its titles' words, sibling record names (user-ruled 2026-09-22, decision `pull-quality-closed-at-the-floor-of-retrieval-mechanics-phrasing-rule-no-new-mechanism`).
- **Stage retrieval before work.** Query the area you are about to touch, **articles first, code second** — the store is current reality *and* rationale; the code is only the implementation. Delivery surfaces an owning article when you touch its files, but cannot cover unowned territory nor tell you where to look. The duty stays yours.

## Reconcile-always (every affected article, every change)

- **Every change updates the knowledge base to match, before the work is done.** An un-reconciled change makes the store lie; that is drift, and drift is what breaks the store's authority.
- **Reconcile *every affected* article** — the one owning the touched files (`what_it_does`, acceptance criteria, `files[]`, a history entry) **and** any article whose described behavior or dependencies the change invalidates; follow `relies_on` / `relied_by`.
- **Which field carries paths is PER TYPE:** `feature_article` → `files[{path, role}]`; `decision`/`anti_pattern`/`research_finding`/`todo` → `file_keys[]`; `reference_material` → `location`. A field the type does not define is refused, never silently dropped.
- **Fix a wrong record FORWARD** with `knowledge_update` — the correction supersedes the error. **Retirement is narrow:** `knowledge_retire(id, in_favor_of)` is for a genuine DUPLICATE, never for a record that is merely wrong, and never by creating a replacement beside the original; the one other case is an obsolete `feature_article` whose files are all gone and that nothing live depends on, retired with `knowledge_retire(id, reason: "feature_removed")` after it is deprecated (`/sterling:cleanup` lists these as retire candidates). **Ask the schema, don't guess it** (`knowledge_schema`), and take the refusal as the authority over the projection. An 8-char prefix resolves when reading and updating; every destroying path demands the full id.
- **Author records to be found.** Titles carry the words a user would say, not changelog prose; triggers and statements are short and subject-dense, with evidence moved to `guidance`, `right_way` or `rationale`; one subject per record; accurate file paths. Push and preflight match only a record's narrow fields (title plus statement or trigger), so a subject that sits only in the body is never found. Decision `make-records-findable-authoring-rule-disclosure-lint-then-blind-experiment`, measured in finding `what-makes-a-record-findable-authoring-traits-astra-fable-october-2026`.

## Conduct rules (Sterling layer)

- **A settled ruling is not a fresh choice.** Never present a question a decision already settles as open: whichever option the user picks becomes a false ruling.
- **Cite rulings by SLUG in durable pointers** (commit messages, briefs, article prose): a slug names the concept and survives supersession; ids version-pin. Where space allows print both — `[slug] (knowledge_get <id>)`. Bare ids stay correct on mechanically-resolved surfaces and in history entries pinned to what was live then. **Never put a bare id in front of a HUMAN** — an identifier shown to a person carries its name beside it, `name (id8)`, name first: names clip, ids never do. Asked to rule on "board 17204d1e" the reader cannot know what they are ruling on, and an unanswerable question still manufactures a ruling.
- **Ask, don't guess — through the AskUserQuestion tool.** EVERY decision put to the user goes through the AskUserQuestion tool form; a question asked in prose — even a numbered section — reads as rhetorical and gets missed (user-stated 2026-08-11), so it does not count as having asked. Before the question reaches the user, run `knowledge_preflight(text)` on its subject — a `verify_targets` verdict means the store already governs it; fold the ruling into the question (or drop it) BEFORE asking.
- **A ruling exists only if it came through the question form:** user-stated 2026-09-22, verbatim: *"I only rule using question forms. So if there wasnt one i cant rule"* — an answer given in prose, a form answered with a question, or an interrupted form is not a ruling; put the form again. Safe-default-and-proceed only for a reversible choice needing no authorization, never for a gate.
- **Instruction-file proposals replace memory.** Auto-memory is off in every Sterling project (decision `sterling-projects-run-with-claude-code-auto-memory-off`). When the user corrects you or states a lasting preference or convention — the moment Claude would once have written a memory — draft the bullet in AGENTS.md's own style (every rule a project adds goes into AGENTS.md, which every host reads; CLAUDE.md and GEMINI.md hold only Sterling's generated layer, decision `project-rules-live-in-agents-md-claude-and-gemini-md-hold-only-the-sterling-layer`), run `knowledge_preflight` and check AGENTS.md so you never propose what is already covered, and at the next natural pause — never mid-task — put it to the user through the question form: add, or not. Facts with currency or rationale still go to the store, not the files. User-ruled 2026-09-28: *"if it would have been added to memory before, then it properly doesnt hurt to ask"* — a correction the user had to make once should never need making twice.
- **Run `sterling:de-ai-writing` on prose deliverables before they ship.** Docs, READMEs, store records, PR and commit bodies, and user-facing copy get a pass (the skill's scanner plus a read) before they are written or committed. Code, tests and chat replies don't; they follow the plain-writing rule in AGENTS.md.
- **Solve, don't board.** Inside the current task's scope, fix a finding in-session; board only what cannot be done now and say why (user-stated 2026-07-27). Neither gets silently parked. A user ask is different: **every user ask is boarded at intake**, one item per distinct ask before the first dispatch, even when work starts at once (decision `every-user-ask-is-boarded-at-intake-with-slim-blocked-by`; user-stated 2026-10-01: *"when i ask for something, whether it is one thing or multiple things, tasks are created on the board eventhough the works starts right away. It is prevent something being forgotten or lost if we crash."*). A multi-area ask is split into one-area, mergeable items wired by `blocked_by` under one `objective`, because smaller items block less (decision `board-asks-split-at-intake-into-mergeable-one-area-items`). Plan their order at intake and run every unblocked lane in parallel.
- **Close-on-commit: a commit that fulfils a board item pays it** — `board_remove` in the same breath, citing the commit. A user task also takes an `outcome`: `done` (with the commit as `evidence`), `dropped`, `superseded` or `duplicate`; the removal journal keeps it. **A board item states its EVIDENCE, not its conclusion:** quote the deciding `file:line` or the measured number; "the facing is broken" cannot be re-checked and rots invisibly. Re-verify an item against HEAD before dispatching at it — refreshing its BLOCKER is not re-checking its DEFECT. The evidence rule covers items FOUND during work; a user-ask item instead records the user's words verbatim and its acceptance. When work leaves the main tree (a worktree or PR branch), the item text names the branch, so a session after a crash can resume it. A partly-done item is rewritten, never removed.
- **When the platform disagrees with the design, STOP — never silently adapt.** Claude Code's hook, frontmatter and transcript mechanics move between versions. If verified current behavior contradicts what a record or this file assumes: report the discrepancy with the doc reference AND a proposed degraded-loud fallback, then wait for approval.
- **Mechanism inventories do not live in THIS file — the store is the census.** Never copy in what a self-describing surface answers: record shapes (`knowledge_schema`), the hook roster (`hooks.json`), the anti-pattern set (`knowledge_query`). A summary of the store is a second copy that rots. This file carries durable conventions and their justifying incidents; repo layout and the tool-agnostic invariants are in AGENTS.md; no-hand-maintained-docs is there too (one copy only).
