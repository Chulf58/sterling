# Drain the queue SOP (§3.2.7)

Trigger: /sterling:drain, the H1 banner maintenance count, or a TUI queue review. Scope: the **SYSTEM maintenance queue** (`maintenance_query`, i.e. `board_query` source `system`) **outside an active run** — a live run's reconciliation is H9 / dispose-run territory, not this. The user board (source `user`) is the human's own surface — never auto-removed; report its count only.

The one rule the queue runs on: an item leaves only **after** its fulfilling artifact actually exists (P4 — done = removed by the artifact-write; system removals are logged to the queue-drain audit trail). For the two drift lanes (`reconcile_needed`, `refresh_reference`) the fulfilling `knowledge_update` **is** the removal — the server auto-drains any open item whose `feature_link` sits in the updated record's supersede chain (decision `8ecd435f`); a `board_remove` after a genuine reconcile therefore throws `board_remove: no record`. Every other lane leaves via `board_remove`. Removing an item you have not fulfilled makes the store lie — the exact drift the queue exists to prevent.

1. **Snapshot first, act second.** `run_state` — if a run is active, stop (its queue is not yours to drain). Then `maintenance_query`, group the items by `system_reason`, and report the counts before touching anything.

2. **Fulfil the knowledge-debt items** — one item → one fulfilling artifact → `board_remove`:
   - `reconcile_needed` — first **resolve `feature_link` forward to the ACTIVE record** (chase `superseded_by` to the head of the version chain): the link is pinned to whatever version was current when H7 fired, which may be several supersessions stale, and you must never read against — or `knowledge_update` — a superseded record. Then check **whether the debt is already paid** before touching anything: a `reconcile_needed` item routinely outlives the reconcile that should have closed it (the article was updated but the item never `board_remove`d), and for a file CO-OWNED by several articles the change may have been reconciled into a *different* owner than the one named here. The mechanical "already reconciled?" signal is the content baseline (decision `57d9a52d`): a `knowledge_query` of the owning article that does **not** raise `verify_before_use` for the touched file means its `file_baselines` already matches the file's current bytes — i.e. the article was last reconciled against exactly this content. For a co-owned file, run that check on the article that actually owns the changed behavior (`knowledge_query file_keys:["<path>"] types:["feature_article"]` lists every co-owner).
     - **Already reconciled** (baseline matches / `verify_before_use` not raised, and the prose covers the change) → confirm the owning toolchain is green, then `board_remove` with **NO** `knowledge_update`. A no-op version bump whose history entry claims a reconcile that added nothing is itself drift — the closing rule forbids it.
     - **Genuinely behind** (baseline differs or is absent, or the prose lags the code) → **verify the code is green first** (run the owning toolchain's tests; never reconcile an article to describe broken code), then `knowledge_update` **every affected** article (what_it_does, ACs, files[], a history entry), following `relies_on` / `relied_by` — not only the one named. The update auto-drains the item (decision `8ecd435f`); `board_remove` only a **survivor** — an item still open because the change was reconciled into a *different* co-owning article whose supersede chain does not cover this item's `feature_link`.
   - `capture_owed` — capture the session's knowledge **born structured** (`decision` / `anti_pattern` / `research_finding`, or article reconciliation), never parked in a note. Then `board_remove`.
   - `research_owed` — write the durable knowledge record (`research_finding`, or `decision` if the finding resolves a design question) from the queries the item text carries. Then `board_remove`. If the user states nothing durable was learned from those queries, `board_remove` without creating a record — the item text carries the queries so the decision is traceable.
   - `article_missing` — `knowledge_create` the owning `feature_article` (or, for a governing doc, the repo-located `reference_material`) for the unowned `file_keys`. Then `board_remove`.
   - `concept_article_missing` — `knowledge_create` (or `knowledge_update`) the CONCEPT article for the family named in the item text: a `feature_article` with `concept_family` set — what the concept IS + members, INTENT + INTERACTIONS cross-referenced by sibling slug, owning code files (decision `7208729b`). General capture does not fulfil this lane. Then `board_remove`.
   - `refresh_reference` — re-read the cited reference, confirm it still holds, `knowledge_update` to clear the stale flag — the update auto-drains the item (decision `8ecd435f`); `board_remove` only a survivor.
   - `stale_research` — re-verify the `research_finding`'s claim (dispatch a `researcher` if it needs the web), update both clocks. Then `board_remove`.
   - `wire_in_dormant` — wire the dormant article's feature in; if it is genuinely abandoned, route to cleanup instead. `board_remove` once resolved.
   - `state_review` — the article's METADATA contradicts reality (decision `8122ed3a`'s sibling, board db7cd16c): it declares `planned`/`dormant` while the files it owns hold real code, or its `files[]` roles are still flagged `unverified`. **Read the prose against the code BEFORE changing anything.** In the case that produced this lane, all ten acceptance criteria HELD and the prose was accurate — only the `state` field and the unwritten roles were wrong, so the fix was a metadata correction plus a `files[]` role pass, NOT a rewrite. Assuming the prose is as stale as the metadata is how a correct article gets damaged. Then `knowledge_update` the state (and clear the `unverified` flags for the roles you actually wrote from the file), and `board_remove` — this lane does NOT auto-drain, because the drift auto-drain is scoped to the two drift reasons.

   **A `reconcile_needed` item whose file is MISSING is a different animal — the procedure above does NOT close it.** The two look identical in query output (both `reconcile_needed`, both carrying a `feature_link`), but the arms differ at the root: a content mismatch is STALENESS, which a `knowledge_update` resolves and auto-drains, while absence is ABSENCE — **no write makes a file appear.** The missing-file check is a pure function of the current working tree, re-evaluated on every `knowledge_query`, so it re-fires immediately after any reconcile that does not change that fact. Following the staleness procedure on it produces an endless series of history entries that add nothing — the very "version bump claiming a reconcile that added nothing is itself drift" failure the closing rule forbids. Observed in a consuming project: a full, correct negative-result entry appended at 06:24, and a brand-new identical item fired at 07:28.
   - **The mechanism now asks git before concluding, so a `reconcile_needed` on an absent file means it exists on NO ref.** Since 2026-08-03 (decision `30d18443`) the read-time absence arm probes HEAD and then local branches; a file found on any of them mints an INFORMATIONAL **`file_parked`** item instead, which demands no reconcile. So a `reconcile_needed` naming a missing file is now a trustworthy deletion signal rather than an ambiguous one — that is `deletion_candidate` territory: route it to `/sterling:cleanup` (step 3) rather than editing the article here.
   - **Still verify rather than assume, because `ls` proves nothing but working-tree absence.** The probe degrades to the deletion reading whenever git cannot answer (no repo, git missing, more than 40 local branches), deliberately — suppressing a real deletion would be the worse failure. If the item surprises you, check by hand: `git cat-file -e HEAD:<path>`, then `git for-each-ref refs/heads`. A consuming project asserted two files deleted as a "VERIFIED FACT" from `ls`; a librarian refused both writes and git proved both alive on an unmerged branch.
   - **A `file_parked` item is not yours to close by writing anything, and `files[]` must NOT be edited.** Dropping the path is the tempting fix and it is exactly wrong — the path becomes valid again when the branch lands, so dropping it corrupts the article. The item closes on the MERGE: `/sterling:merge` sweeps every `file_parked` item whose paths are all present again (P4 — removed by the event that ends its life). Leave it alone; if you are draining after a merge that the gate did not run, `maintenance_remove` the ones whose files are back.

   **Delegating the mechanical half to the `librarian` (P8: judgment stays here, clerking goes cheap).** The classification above — co-tenant vs substantive, already-paid vs genuinely behind, stale vs absent — is judgment and stays YOURS. Once you have classified, the resulting *writes* are mechanical and may be dispatched in bulk to the `librarian` agent instead of performed inline:
   - Dispatch it work order **(a)** — the co-tenant / already-behind-but-baseline-only items as `{maintenance_id, feature_link, verdict}` triples — and it performs the minimal `{"state": "active"}` refresh per item, which auto-drains each one.
   - Dispatch it work order **(b)** — your own drafted update bodies keyed by article id — and it applies them byte-for-byte. Drafts must carry the **full** history array: history REPLACES on update, so a truncated draft destroys history (the librarian is instructed to stop and report rather than write one). **For a long STRING field, brief it to use `knowledge_edit(id, field, find, replace)` instead** — a registry-style article can outgrow its own round-trip (`hooks-suite`'s `what_it_does` is one ~26k-token string that cannot be read whole, so no agent can retransmit it byte-perfect, and one asked to try will correctly REFUSE rather than risk a silent transcription corruption). Give it a `find` you know is unique; the tool refuses both zero and multiple matches.
   - Dispatch it work order **(c)** — a list of `{maintenance_id}` for items you have confirmed fulfilled — and it closes them with **`maintenance_remove`** (system-source only; the user board stays read-only to it). Before that grant it could read the queue and close nothing, so every `article_missing` / `capture_owed` / `concept_article_missing` / `research_owed` item bounced back to the conductor (board afeae7d9, decision `9948475b`).
   - It will REFUSE anything substantive and hand it back with a one-line reason. That refusal is correct — draft the reconcile yourself and re-dispatch as (b), never tell it to author.
   - It reports drained ids → new article ids plus the post-drain `maintenance_query` count; that report is your audit input for step 4. Delegation is optional — for one or two items, doing it inline is cheaper than briefing an agent (P1).

3. **Delegate the gated items — never auto-resolve them inside a drain** (P1: keep the gate where being wrong is costly):
   - `deletion_candidate` → hand to `/sterling:cleanup` (the §8.4 gated deletion SOP). Leave the item; cleanup's deletion artifact removes it.
   - `promotion_review` → present the candidate to the human as a keep-or-promote decision; only on yes run `knowledge_promote` (promoting drains the matching review). Never auto-promote.

4. **Verify + close.** `npm run check` and the touched toolchains' tests green. `maintenance_query` again: the queue is empty, or holds only the gated items you delegated and reported. State what was drained (the drain log is the audit) and what was handed off, to whom.

Drain is never a place to invent a reconciliation or claim a capture you did not perform — and never a back door around the cleanup or promotion gates.
