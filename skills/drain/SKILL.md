# Drain the queue SOP

Trigger: /sterling:drain, the H1 banner maintenance count, or a TUI queue review. Scope: the **SYSTEM maintenance queue** (`maintenance_query`, i.e. `board_query` source `system`). The user board (source `user`) is the human's own surface — never auto-removed; report its count only.

The one rule the queue runs on: an item leaves only **after** its fulfilling artifact actually exists (P4 — done = removed by the artifact-write; system removals are logged to the queue-drain audit trail). Closure is always an EXPLICIT claim, never implicit — a write that does not name the item leaves it OPEN and its receipt warns naming it. There are two ways an item leaves:

- **A resolving write** — the fulfilling write names the item via `resolves: [<item id>]`, validated before the write lands (the item must be open, in an admitted lane, and keyed to the written record or one of its supersedes-chain ancestors; a refusal writes nothing). Admitted shapes (`packages/mcp-server/src/tools.ts`, `UPDATE_RESOLVABLE_LANES` and `APPEND_JOIN_RESOLVABLE_LANE`):
  - `knowledge_update` / `knowledge_edit` / `knowledge_append` for `reconcile_needed`, `refresh_reference`, `stale_research`, `wire_in_dormant` and `state_review`;
  - `knowledge_append` to `files` on an EXISTING `feature_article`, where at least one appended path is one of the item's `file_keys`, for `article_missing` (joining the file to an article that already covers it);
  - `knowledge_split` for the `article_oversize` item of the article it splits.
- **`board_remove` / `maintenance_remove`** after the artifact exists — every other lane, and a `knowledge_create` discharge (create takes no `resolves`).

**Cross-store refusal.** If a `resolves` claim is refused because the target record is physically held by a domain store rather than the project store (maintenance items are project-local), follow the refusal's remedy in order: perform the write WITHOUT `resolves`, verify it paid the lane, then `maintenance_remove` the item.

Removing an item you have not fulfilled makes the store lie — the exact drift the queue exists to prevent.

1. **Snapshot first, act second.** `maintenance_query` (i.e. `board_query source:"system"`), paging (`cursor` = `next_cursor`) until `capped` is false — a capped page is a window, not the queue. Group the items by `system_reason` and report the counts before touching anything. The default projection clips each item's text at 240 chars, so `board_get` each item before classifying it.

2. **Fulfil the knowledge-debt items** — one item → one fulfilling artifact → the closing step for its lane **(exact full id only — `board_remove`/`maintenance_remove` resolve by exact id, never a prefix; a prefix could silently retarget a different, live item and destroy it. The same exactness binds every `resolves:` claim you pass on a discharging write. The failure mode is a loud refusal, not damage — it costs a round trip, nothing more)**:
   - `reconcile_needed` — the `feature_link` id is the active record: update/edit/append mutate the record IN PLACE with a server-owned version bump, so ids move only on genuine supersession or retire. Check **whether the debt is already paid** before touching anything: a `reconcile_needed` item routinely outlives the reconcile that should have closed it, and for a file CO-OWNED by several articles the change may have been reconciled into a *different* owner than the one named here (`knowledge_query file_keys:["<path>"] types:["feature_article"]` lists every co-owner). **An absent annotation is not proof of freshness.** A `knowledge_query` result without `verify_before_use`/`baseline_drift` proves nothing unless its `provenance` reads `checked` — `unavailable:<reason>` means the check never ran. Require positive evidence: `provenance: checked` with no drift annotation on the owning article, AND prose that covers the change.
     - **Already reconciled** (positive evidence as above) → `board_remove` with **NO** `knowledge_update`. A no-op version bump whose history entry claims a reconcile that added nothing is itself drift — the closing rule forbids it.
     - **Genuinely behind** (drift raised, or the prose lags the code) → when the rewrite describes CHANGED behaviour, run the owning toolchain's tests first and describe what they show: green, or the known failures stated honestly in the article (a history entry naming them) — never withhold the reconcile because a test is red, and never describe as working what the tests show broken. A rewrite that only corrects prose to match unchanged code needs no test run. Then `knowledge_update` **every affected** article (what_it_does, ACs, files[], a history entry), following `relies_on` / `relied_by` — not only the one named, passing `resolves: [<this item's id>]` on the write that fulfils it (the write is not a claim by itself; naming it is what drains it). A refusal (wrong id, wrong lane, or an item keyed to a different article's chain) means STOP and report — never write without the claim, and never `board_remove`/`maintenance_remove` around the refusal (the cross-store remedy above is the one exception, and the refusal names it). `board_remove` only a **survivor** — an item still open because the change was reconciled into a *different* co-owning article and could not be named on this write.
   - `capture_owed` — capture the session's knowledge **born structured** (`decision` / `anti_pattern` / `research_finding`, or article reconciliation), never left as loose prose. Then `board_remove`.
   - `research_owed` — write the durable knowledge record (`research_finding`, or `decision` if the finding resolves a design question) from the queries the item text carries. Then `board_remove`. If the user states nothing durable was learned from those queries, `board_remove` without creating a record — the item text carries the queries so the decision is traceable.
   - `article_missing` — if an existing `feature_article` already covers the unowned file, JOIN it: `knowledge_append` the path to that article's `files` with `resolves: [<item id>]`. Otherwise `knowledge_create` the owning `feature_article` (or, for a governing doc, the repo-located `reference_material`) for the unowned `file_keys`, then `board_remove`.
   - `concept_article_missing` — `knowledge_create` (or `knowledge_update`) the CONCEPT article for the family named in the item text: a `feature_article` with `concept_family` set — what the concept IS + members, INTENT + INTERACTIONS cross-referenced by sibling slug, owning code files. General capture does not fulfil this lane. Then `board_remove` (or `resolves` on the update, when it is an update).
   - `refresh_reference` — re-read the cited reference, confirm it still holds, `knowledge_update` to clear the stale flag, passing `resolves: [<item id>]` on that write; `board_remove` only a survivor.
   - `stale_research` — re-verify the `research_finding`'s claim and update both clocks, passing `resolves: [<item id>]`. Re-verification, local or on the web, goes to a `researcher` (it has WebSearch and WebFetch); a question of judgement goes to an Astra consult.
   - `wire_in_dormant` — wire the dormant article's feature in; if it is genuinely abandoned, route to cleanup instead. Close with `resolves` on the article write that records it, or `board_remove` once resolved.
   - `state_review` — the article's METADATA contradicts reality: it declares `planned`/`dormant` while the files it owns hold real code, or its `files[]` roles are still flagged `unverified`. **Read the prose against the code BEFORE changing anything.** In the case that produced this lane, every acceptance criterion HELD and the prose was accurate — only the `state` field and the unwritten roles were wrong, so the fix was a metadata correction plus a `files[]` role pass, NOT a rewrite. Assuming the prose is as stale as the metadata is how a correct article gets damaged. Then `knowledge_update` the state (and clear the `unverified` flags for the roles you actually wrote from the file), passing `resolves: [<item id>]`.
   - `article_oversize` — the article's non-history body is over the `article_oversize_chars` threshold; the deed is a split (drain verb `split`). Split it per the concept-article granularity rubric with `knowledge_split`, passing `resolves: [<item id>]`. If a re-measure shows it back under the threshold, say so and `maintenance_remove` the item.
   - `restore_performed` — no code path mints this lane today (the reason is registered in `packages/schemas/src/records.ts`, but nothing enqueues it). If you see one, report it as an anomaly rather than working it.

   **A `reconcile_needed` item whose file is MISSING is a different animal — the staleness procedure above does NOT close it.** A content mismatch is STALENESS, which a `knowledge_update` resolves; absence is ABSENCE — **no write makes a file appear**, and the check re-fires on every `knowledge_query` until the article stops claiming the path. Following the staleness procedure on it produces an endless series of history entries that add nothing. Before minting, the read-time absence check asks git (`packages/mcp-server/src/tools.ts`, the `parkedOnRef` probe):
   - **Found on a local branch or HEAD** → an informational **`file_parked`** item instead, never `reconcile_needed`. It is not yours to close by writing anything, and `files[]` must NOT be edited — the path becomes valid again when the branch lands. It closes on the MERGE: `/sterling:merge` sweeps every `file_parked` item whose paths are all present again, or were verifiably deleted between the merge endpoints (`scripts/lib/parked-close.mjs`). If you are draining after a merge the gate did not run, `maintenance_remove` the ones whose files are back or whose deletion git proves.
   - **Never tracked on any reachable ref** → a `deletion_candidate` item, not `reconcile_needed`: route it to `/sterling:cleanup` (step 3).
   - **Once tracked, now absent** (real git history) → the `reconcile_needed` you are looking at, and an ordinary, closeable reconcile: the article must stop claiming the path. Check the co-owners first (`knowledge_query file_keys:["<path>"]`) so no surviving behavior is orphaned, then drop the path from `files[]` (`knowledge_array_remove`, or a drafted update) with `resolves: [<item id>]`, and fix any prose that described the file.
   - **Probe failed** (no repo, git missing, an unreadable history) → also minted as `reconcile_needed`, because a failed probe proves nothing. Check by hand (`git cat-file -e HEAD:<path>`, `git rev-list --all -- <path>`); if git cannot answer, report the item as unclassifiable — never guess which reading applies. `ls` proves only working-tree absence.

   **Delegating the mechanical half to the `librarian` (P8: judgment stays here, clerking goes cheap).** The classification above — co-tenant vs substantive, already-paid vs genuinely behind, stale vs absent — is judgment and stays YOURS, and so does authorship: only the conductor drafts store content. The librarian's grant (`agent-templates/librarian.md`) is update-shaped knowledge writes (`knowledge_update`/`append`/`edit`/`array_remove`) plus board and queue writes (`board_add`/`board_update`/`board_remove`, `maintenance_remove`), every one applying conductor-drafted content verbatim; it never creates records. Once you have classified, the resulting *writes* may be dispatched to it in bulk:
   - Work order **(a)** — the co-tenant items as `{maintenance_id, feature_link, verdict}` triples — and it performs the minimal `{"state": "active"}` refresh per item, passing `resolves: [<maintenance_id>]` on that same write.
   - Work order **(b)** — your own drafted update bodies keyed by article id — and it applies them byte-for-byte. Prefer history ENTRIES for `knowledge_append`; a draft that passes `history` through `knowledge_update` must carry the **full** array, because update REPLACES it. **For a long STRING field, brief it to use `knowledge_edit(id, field, find, replace)` instead** — a registry-style article can outgrow its own round-trip, and an agent asked to retransmit one will correctly refuse. Give it a `find` you know is unique; the tool refuses both zero and multiple matches.
   - A list of `{maintenance_id}` for items you have confirmed fulfilled — it closes them with `maintenance_remove`.
   - It will REFUSE anything substantive and hand it back with a one-line reason. That refusal is correct — draft the reconcile yourself and re-dispatch as (b), never tell it to author.
   - It reports drained ids plus the post-drain `maintenance_query` count; that report is your audit input for step 4. Delegation is optional — for one or two items, doing it inline is cheaper than briefing an agent (P1).

3. **Delegate the gated items — never auto-resolve them inside a drain** (P1: keep the gate where being wrong is costly):
   - `deletion_candidate` → hand to `/sterling:cleanup` (the gated deletion SOP). Leave the item; cleanup's deletion artifact removes it.
   - `promotion_review` → present the candidate to the human as a keep-or-promote decision; only on yes run `knowledge_promote` (promoting drains the matching review). Never auto-promote.

4. **Verify + close.** If the drain changed files, run `npm run check` and the touched toolchains' tests; a store-only drain needs neither. `maintenance_query` again (paged until `capped` is false): the queue is empty, or holds only the gated items you delegated, the `file_parked` items waiting on their branch, and anything you reported as unclassifiable or anomalous. State what was drained (the drain log is the audit) and what was handed off or left, to whom and why.

Drain is never a place to invent a reconciliation or claim a capture you did not perform — and never a back door around the cleanup or promotion gates.
