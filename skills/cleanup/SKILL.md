# Cleanup SOP

Trigger: /sterling:cleanup or maintenance-queue review. Input: `deprecated`/`dormant` articles + `deletion_candidate` queue entries. The articles' file/dependency data is the evidence that makes deletion safe.

1. **Deletion plan:** from the candidate articles, list exactly which files/exports die and which articles claim dependents. No dependents = deletable; any active `relied_by` = blocked until released. An article's `files[]` is every file the feature touched, shared host files included, so it is not the deletion set. `cleanup-plan.mjs` sorts each path of a deletable candidate into one bucket: `delete` (on disk, no live owner, and no other tracked file references its filename, its stem, the stem in PascalCase or camelCase, or for a `.gd` file its declared `class_name`), `release` (a live article, meaning any article that is not deprecated, also owns it), `absent` (not on disk) or `keep` (another file references it, or the reference check could not run). References among one article's own dying paths do not count, so files that only mention each other can go together. A document such as `README.md` or `CHANGELOG.md` is matched by its path, not its bare name. The planner takes candidates only from the article's `files[]`: a leftover the article never listed, such as a test fixture, is not offered, so add it to `files[]` first and run the planner again (decision `cleanup-plans-only-files-an-article-lists`). Only `delete` paths die. A deprecated or dormant article none of whose paths exists on disk is not a deletion candidate; a deprecated one is listed under `retire_candidates` instead (step 5). A dormant article can be a candidate; a dormant co-owner still protects a shared file. Tracing which files/exports die is repo-grounded read-only investigation that can go to a read-only lane; which articles claim dependents needs the store's `relied_by` data, so that piece stays on a Claude agent — Codex has no knowledge tools.
2. **Confirm the map once:** present the whole deletion map — "these N dormant features own these files with no active dependents" — and the human confirms it in one answer, striking any item they want kept (decision `skill-ceremony-scaled-to-risk-after-2026-09-26-audit`). Group the map by article and bucket, and give each path its reason.
3. **Execute carefully:** use the confirmed deletion map as the boundary. Remove only confirmed `delete` paths, through `node "${CLAUDE_PLUGIN_ROOT}/bin/fs-remove.mjs" <path>...` — never raw deletion — so the removal is registered and owning articles get reconciled, and keep file keys coherent. A `release` or `absent` path is a store edit, never a deletion: drop it from that article's `files[]`. A `keep` path stays on disk and in the article.
4. **Verify:** run the relevant build and tests, inspect the deletion diff, and obtain an independent review appropriate to the risk before committing.
5. **Retirement:**
   - **Tests.** Never delete a mechanism's test file wholesale (anti-pattern `deleted-test-file-takes-coverage-of-surviving-code-with-it`). Split its assertions into those whose subject is gone and those that exercise code that still ships; port the second set to a surviving test file, then delete the rest.
   - **Articles.** `knowledge_update` each owning article to say what happened: `state: "deprecated"` (or the article's ownership rewritten when only part of it died), with the dead paths dropped from `files[]` and a history entry. Never drop the last `files[]` entry: the store keeps at least one owned file per article and refuses to trim it to nothing.
   - **Removed features.** `cleanup-plan.mjs` lists a deprecated article whose every path is gone under `retire_candidates`, with the tree its absence was checked against and its blockers: an active article that relies on it in either direction, a path still present or parked on another branch, or a working tree that does not resolve. Show the human the list once, together with the deletion map. For each unblocked entry they confirm, call `knowledge_retire(id, reason: "feature_removed")` with the full UUID and no `in_favor_of`. The record is kept with status `superseded` and no successor, its dead paths stay in `files[]` as historical ownership, queries stop serving it, and `knowledge_get` shows `retired: feature removed`. `knowledge_retire` checks every condition again when it runs and names what failed when it refuses; leave a refused or blocked entry as it is. A genuine duplicate still goes through `knowledge_retire(id, in_favor_of)` (GitHub #217, user-ruled 2026-10-27, narrowing decision 9948475b).
   - **Board and queue.** Entries are removed by the deletion artifact (P4). Removal operations take the exact full UUID, never a prefix.

Cleanup is its own unit of work — an implementor told to "tidy while you're at it" is out of scope by design.
