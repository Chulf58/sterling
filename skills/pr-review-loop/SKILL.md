# PR review loop (work mode)

Decision `project-mode-hobby-work-toggle-decides-flow`. Sol (the `reviewer` agent on Opus when Sol is capped) has already reviewed before the PR opened; Copilot now reviews on GitHub. When the loop ends clean and the auto-merge switch is on (the default), you squash-merge the PR yourself (see "Auto-merge on a clean end" below; decision `work-mode-pr-auto-merge-when-copilot-loop-ends-clean`). Otherwise a human merges it.

## Owner and tools

Keep the default `--timeout` (540s, under the 10-minute Bash window); a `timeout` result means run it again, and it is not a round. A `no_review_requested` result is not a timeout: never re-run it unchanged, follow step 1.

- **Fixes go to an implementor** (brief: the finding, the file, the acceptance). You disposition findings and reply on GitHub.
- Everything uses `gh`; the helper binds the repo to origin.

## State lives on the PR

One **progress comment** on the PR holds the state: round, consumed review id, reviewed head SHA, status (`waiting|responding|clean|capped|escalated`). Create it with `gh api repos/<o>/<r>/issues/<n>/comments -f body=...` and update that same comment with `gh api -X PATCH repos/<o>/<r>/issues/comments/<id> -f body=...`. Mark its body so you can find it again (e.g. first line `<!-- sterling-pr-review-loop -->`). **On re-entry** (a new session, after compaction), reread the PR and that comment and continue from them; never reset the round count.

## One round

1. Wait: `node "${CLAUDE_PLUGIN_ROOT}/bin/pr-review-wait.mjs" <pr_url> --since-review <consumed id> --head <pushed sha>`, adding `--request-copilot` on the first wait after **every** push (see step 3). Pass the full sha; a short one (7-40 hex characters) is accepted and matched as a prefix, anything else is refused. It returns `{status, head_sha, review, comments, previously_missed, previously_missed_unparsed, body_findings_without_comments, copilot_request, copilot_review_pending, observed_copilot_login, stale_review}`.
   **Every poll lists all of the PR's reviews**, and `review` is the OLDEST completed Copilot review above the `--since-review` watermark, on ANY head, so no review is ever skipped and you do not list them by hand. `stale_review: true` means that review is not of the current head (it reviewed an earlier head, often one Copilot started before your push landed, or the PR head is not yet `--head`). Disposition its findings like any other (step 2); it is never the clean review of the head. **Advance the consumed review id (the `--since-review` watermark) only after every comment of that review is dispositioned**, then call again at once: the next unconsumed review comes back before any wait. A later review never hides an earlier one's findings.
   **The wait waits only while Copilot has a review request pending.** With no unconsumed review and no Copilot request on the PR, nothing will arrive, so it ends with `status: 'no_review_requested'` (exit 3) instead of timing out. It first checks once more after `--recheck-delay` seconds (default 10), because a request made seconds earlier may not show on GitHub yet. Run the wait again with `--request-copilot`; if it ends with `no_review_requested` again, or `copilot_request.requested` is false (the mutation failed), the request is not reaching GitHub: ask the user whether to re-request by hand. `timeout`, `no_review_requested` and `error` are never clean. A `timeout` means a request is pending (`copilot_review_pending: true`) and Copilot has not finished; run the wait again.
   **Read the review body, not only `comments`.** Copilot can put findings in the body (a "Previously missed" section) with no inline comments. A review whose `comments` is empty but whose `previously_missed` is non-empty is NOT clean: disposition each listed finding. The helper reads list items and the nested `<details>` blocks Copilot writes one per finding (returned as "title (path:line): text"). `previously_missed_unparsed: true` means the section is there but the findings read do not match it (none, or not the count its heading gives), so read the section in the body by hand (GitHub issue #102). `body_findings_without_comments: true` (any non-blank body with no inline comments) is also NOT clean until you have read the body yourself, because the format is Copilot's and may change; a body that is only an overview with no finding may then be called clean.
2. Disposition **every** finding, and reply to each comment on GitHub:
   - **fixed**: reply only AFTER the fix is pushed, citing the commit SHA ("will fix" is not a disposition);
   - **disagreed**: reply with the reason; a justified disagreement counts as handled;
   - **TASTE** (colours, placement, layout, naming style and the like): escalate to the user through **AskUserQuestion** and leave the comment unhandled until the user rules. Independent technical fixes continue meanwhile. A measurable defect (e.g. contrast failing a ratio) is not taste. If it is ambiguous, escalate. User-stated 2026-09-25, verbatim: *"If copilot start trying to adjust preference things like colours, placement and such, then also escalate it to me"*.
   **Then resolve the thread of every finding you dispositioned** (fixed, with its SHA reply already posted, or disagreed with, with its reason already posted). A reply never resolves a review thread, and an org ruleset with required thread resolution (`required_review_thread_resolution`) keeps the PR BLOCKED while any thread is open (GitHub issue #42). Pass the REST ids of the inline comments (the `comments[].id` the wait returned): `node "${CLAUDE_PLUGIN_ROOT}/bin/pr-review-wait.mjs" --resolve-threads <id,id,...> --pr <n|PR URL>`. It matches each id to its thread, fires the GraphQL `resolveReviewThread` mutation once per thread, and prints `{status:'resolved', resolved, already_resolved, same_thread_as_resolved}` (the last lists a later comment id that sits in a thread this call just resolved). An unknown id or any gh error exits 1 naming it and is never ignored. Do not resolve a thread whose finding is escalated as taste and not yet ruled on, and a `previously_missed` finding with no inline comment has no thread to resolve.
3. **Only if this round's fixes produced a new head**, push through `/sterling:merge` again. Push the fix straight back to Copilot — no Sol, Opus or other reviewer re-checks a loop fix round; Copilot is the reviewer inside the loop (user-stated 2026-09-28: "co-pilot is the reviewer"). The one Sol review (the `reviewer` agent on Opus when Sol is capped) happens before the PR is opened. A round with no fix commits (every finding disagreed with or escalated) is dispositioned directly: no push and no re-arm, and the next wait keeps the same `--head`. The push reuses the PR, pushes the pinned SHA, prints JSON and re-arms the H10 duty for the new head. Copilot does not review the new head until it is re-requested, so **re-request after every push**: the next wait passes `--request-copilot`, with no exception. It fires the GraphQL `requestReviewsByLogin` mutation once before polling and records `copilot_request` as `{requested: true}` or `{requested: false, error}`. A failed request never aborts the wait by itself; with nothing else pending the wait then ends with `no_review_requested`, and the user is asked whether to re-request by hand. Before the first PR, and on a fix push that changes knowledge, reconcile first and then refresh the handoff docs with `node "${CLAUDE_PLUGIN_ROOT}/bin/handoff-projection.mjs"`. This is practice, not a gate.
4. Update the progress comment: round +1, the consumed review id, the reviewed head, the status.

## Ending: three distinct outcomes

- **CLEAN**: a completed Copilot review of the CURRENT head with no remaining actionable findings, and every earlier finding dispositioned. Silence, a timeout, `no_review_requested`, an old-head review (`stale_review: true`) or an unresolved taste comment is never clean. **Clean also means GitHub lets the PR merge**: settling `clean` asks GitHub for `mergeStateStatus`, `reviewDecision`, the head commit's check rollup and every review thread. Any unresolved thread, or a state other than CLEAN, HAS_HOOKS or UNSTABLE (BLOCKED, DIRTY, BEHIND, UNKNOWN, or any state the helper does not know), refuses the settle with `status: 'blocked'`, exit 1, the blockers and unresolved threads named, and the loop stays owed. Resolve the threads (see step 2), or fix or report the blocker, then settle again. UNKNOWN is transient (GitHub computes mergeability lazily): the helper reads once more after `--unknown-retry-delay` seconds (default 3), and if it is still UNKNOWN the settle is refused with a "retry shortly" note, so wait a little and settle again. One exception is reported, not refused: a PR that is BLOCKED with no unresolved thread and `reviewDecision` REVIEW_REQUIRED waits only for a human approval the loop cannot give, so it settles clean with `awaiting_human_review: true`, but only when the head's check rollup (`check_rollup` in the output) is SUCCESS or null (no checks). A failing or pending required check also shows as BLOCKED, so any other rollup refuses the settle and names the check state. A gh failure also refuses the settle.
- **CAPPED**: 5 completed review/response cycles across the PR's lifetime, not per session. Poll attempts do not count.
- **ESCALATED**: a ruling from the user is outstanding (taste or ambiguity), and nothing else is left to do.

Then settle H10's duty. This is a deliberate act, and it names the PR: `node "${CLAUDE_PLUGIN_ROOT}/bin/pr-review-wait.mjs" --settle <clean|capped|escalated> --pr <n|PR URL>`. Each PR has its own armed loop (`.sterling/transient/pr-loops/<n>.json`), so PRs open from several worktrees never replace each other's loop (GitHub issue #104); settling one leaves the others owed. It refuses unless the loop armed for the PR you name is still owed and is for origin's repo; a settled loop is never re-settled (the next `/sterling:merge` push re-arms it). A clean settle prints `merge_state_status`, `review_decision`, `check_rollup`, `mergeable_now`, `awaiting_human_review`, `auto_merge_on_clean`, `auto_merge` and `head_sha`. Report the outcome, the PR link, the round count and whether the PR was merged or can be merged now (`mergeable_now`, or what the PR still awaits) to the user, and put the same line in the progress comment. For `capped` and `escalated` the merge state is not checked and nothing is merged; say so rather than implying the PR is mergeable.

## Auto-merge on a clean end

Decision `work-mode-pr-auto-merge-when-copilot-loop-ends-clean` (user-ruled 2026-10-14: per-project switch, on by default; squash and delete the branch). The switch is `pr_review.auto_merge_on_clean` in `.sterling/config.json`, toggled in the TUI System tab ("Auto-merge clean PRs"); a missing key is on.

**Only a CLEAN settle that printed `auto_merge: true` merges.** The settle is the clean-state check, so always settle first; a merged PR can no longer be settled. `auto_merge` is true only when all of these hold:

- **No open findings**: the loop ended CLEAN as defined above (a completed Copilot review of the current head, every finding dispositioned, no taste comment awaiting a ruling). This is your judgment, made before you run `--settle clean`.
- **Every review thread resolved**: the settle reads every page of the PR's `reviewThreads` through `gh api graphql` and refuses on any `isResolved: false`.
- **Required checks green and nothing else blocking**: GitHub's `mergeStateStatus` is CLEAN, HAS_HOOKS or UNSTABLE. A failing or pending required check, a missing required approval or a conflict shows as BLOCKED, BEHIND or DIRTY, which refuses the settle. A PR that waits only for a human approval settles clean with `awaiting_human_review: true` and `mergeable_now: false`, so `auto_merge` is false.
- **The switch is on**: `auto_merge_on_clean: true`. A value that is not true or false refuses the clean settle before GitHub is asked, naming the value; fix it in the TUI System tab and settle again.

`auto_merge: false` on a clean settle means a human merges: say which reason applies (switch off, or awaiting a human approval). `capped` and `escalated` print no `auto_merge` and never merge.

When `auto_merge` is true, take `<host>`, `<owner>`, `<repo>` and `<n>` from the printed `pr_url` and run these three calls in order. Every call is `gh api`, never `gh pr merge`: under WSL the Windows gh.exe that `gh pr` commands resolve needs a git binary it cannot find (the same reason `/sterling:merge` opens the PR with `gh api`, `commands/merge.md`), and `gh pr merge --delete-branch` also switches and deletes local branches. If gh.exe fails on auth under WSL, pass the token across with `GH_TOKEN` and `WSLENV` as anti-pattern `work-mode-pr-create-fails-with-must-be-a-collaborator-http-4` says.

1. Read the head branch: `gh api --hostname <host> repos/<owner>/<repo>/pulls/<n> --jq '{state: .state, ref: .head.ref, repo: .head.repo.full_name}'`. Go on only when `state` is `open` and `repo` is `<owner>/<repo>`; a PR from another repository is never merged or deleted here, so report it.
2. Merge, pinned to the reviewed head: `gh api --hostname <host> --method PUT repos/<owner>/<repo>/pulls/<n>/merge -f merge_method=squash -f sha=<head_sha>`, with `head_sha` from the settle output. Only a response with `"merged": true` is a merge; note its `sha`. Any other answer is a refusal: 405 (not mergeable: branch protection, a check, a required review), 409 (the head moved since the review) or 422. Then stop: leave the PR open, report GitHub's message word for word, and do not retry. Never pass `--admin` or any other bypass, and never force a refused merge (the decision rules this out).
3. Delete the branch, only after step 2 returned `"merged": true`: `gh api --hostname <host> --method DELETE repos/<owner>/<repo>/git/refs/heads/<ref>`. A 204 deleted it. A 422 "Reference does not exist" means GitHub already deleted it (the repository deletes head branches on merge); report that. Any other failure is reported; the merge stands.

Then put "merged by the conductor (squash `<sha>`), branch `<ref>` deleted" in the progress comment and report the same to the user, with the PR link. Local branches and worktrees are left as they are; say so.

With an unconfirmed identity, **confirm the observed login with the user (AskUserQuestion) before the first CLEAN**; once confirmed, pin it in `pr_review.copilot_logins`, and from then on only that login counts.

The helper matches the reviewer by a Bot login `/copilot/i` while unpinned, and assumes review ids grow monotonically and that `review.commit_id` is the reviewed head. None of this is verified yet.
