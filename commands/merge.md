---
description: Merge the current conductor-direct branch into the base and sweep merged branches — the merge-to-main gate for direct work; in hobby mode the conductor runs it once a task is ready, in work mode it opens the PR.
---

Invoking this is the merge-to-main decision, so run it only once the change is committed and every affected article is reconciled. From the feature branch:

```
node "${CLAUDE_PLUGIN_ROOT}/bin/direct-merge.mjs"
```

It merges the current branch `--no-ff` into the base (the default branch; `--into <b>` to override), deletes that branch, sweeps every other fully merged branch (`git branch -d` refuses unmerged branches), then pushes the base to origin (`--no-push` opts out; no origin skips loudly). It refuses on a dirty tree, when no branch is checked out (detached HEAD, exit 2), when already on the base, when `--branch` names a branch other than the checked-out one (exit 2, before the battery — the battery validates the checked-out tree, so it cannot vouch for another branch; check that branch out instead), or when files beyond generated projections changed without both version fields moving together (`.claude-plugin/plugin.json` and `package.json`; `--allow-same-version` is the deliberate escape). Open `reconcile_needed` items covering changed files are disclosed on stderr with their paths and age, never refused (decision merge-discloses-derived-drift-never-refuses-on-it). Report the merged branch, swept list, and whether the push landed.

Before the merge action, the gate also runs the `npm run check` consistency battery (skipped, loud, on a project with no `check` script) and refuses on failure with one refusal, `the consistency-check battery FAILED`, followed by the battery's own output. Read that output for the cause: among the checks it can name are a STALE BUILD (`src` newer than `dist` — validating a stale build proves nothing; run `npm run build` first) and STALE GENERATED PROJECTIONS (`architecture.md` / `rulings.md` no longer match the knowledge base they're generated from — regenerate and commit them).

**Project mode decides the flow** (`mode` in `.sterling/config.json`, switched in the TUI System tab; a missing key is `hobby`, any other value refuses with exit 2 before anything runs).

- **Hobby** — everything above: the direct merge into the base.
- **Work** — the same preflight (dirty tree, version fields, `npm run check`; reconcile items are disclosed, not refused), then it pushes the feature branch and opens a PR with `gh api --hostname <host> --method POST repos/<owner>/<repo>/pulls` (head, base, title and body as fields; `gh pr create` is not used, because under WSL the Windows gh.exe it resolves needs a git binary it cannot find), its title and body taken from the branch commits and ending with the PR attribution line. An open PR for the same repo, head AND base is reused: the push updates it and no second PR is created; more than one such PR refuses (exit 1). It never checks out, merges into or pushes the base, never sweeps branches and never runs the post-merge repairs; a human merges the PR.
  - **The repo comes from origin.** It is parsed from origin's fetch URL (https, `ssh://` or `host:owner/repo`), never from gh's default repo, and passed to every `gh` call. Every effective push destination (`git remote get-url --push --all origin`, so `pushurl` and `pushInsteadOf` included) must be that same repo, or it refuses with exit 2 before pushing and names each destination.
  - **The push is pinned** to the SHA the preflight and battery checked (`git push origin <sha>:refs/heads/<branch>`, upstream set as config), so a commit that lands during the battery never ships. `--branch`, when given, must be the checked-out branch (see above).
  - **A failed create, or a create response that is not a PR, is followed by a lookup** for the repo, head and base: a PR found there is reported as reused (exit 0); otherwise the PR state is UNKNOWN (exit 1, never "no PR"), with the check command. A successful 201 is trusted with no read-back. Rerunning is safe: it reuses an open PR or creates one, and the push is a no-op. A PR opened by hand is reused, and the review loop armed, when /sterling:merge is rerun on the branch.
  - **Refusals** with exit 2, before the battery: an invalid `mode`, `--no-push` (a PR needs a pushed branch), `gh` missing or not logged in for origin's host (run `gh auth login`), no GitHub-shaped `origin`, mismatched push destinations, or a `--branch` other than the checked-out branch.
  - **Stdout is one JSON object on every work-mode exit**, success or refusal: `{"mode":"work","ok":…,"stage":…,"error":…,"exit":…,"branch":…,"pushed":…,"pr_url":…,"pr_number":…,"created":…}`. `stage` names where it stopped (`done` on success); human text goes to stderr. The one exception is an exit before the mode is known (a bad `--target` argument, or an unreadable or invalid `mode`): it prints on stderr only, as in hobby.

  Report the PR URL and whether it was created or reused. A work-mode run that creates or reuses a PR also arms H10's 'PR review loop owed' duty (`.sterling/transient/pr-loop.json`, status `owed`, the pushed head). The next step is the Copilot review loop: follow the `pr-review-loop` skill (`skills/pr-review-loop/SKILL.md`); Sol has already reviewed before the PR.

Read the first line before reacting to a non-zero exit: it does **not** always mean the merge failed. When the merge lands but a post-merge step does not — stale bundles after git auto-merged `hooks/*.mjs`, a `npm run build` failure on the merged tree, or a failed branch sweep — the gate exits non-zero with `THE MERGE SUCCEEDED` first and the remedy after. Re-running or hand-merging in that state is wrong; do the named remedy on the base branch instead.
